**1. 最值得注意的设计趋势**

**趋势一：权限边界从 prompt 下沉到执行环境。** Muse 的 Secure VM、Cue 的每 agent 独立 email/phone/wallet/电脑，本质是同一件事——不再指望模型"自觉"，而是让越权在物理上不可能发生。模型看不到真密码，比写一百条系统提示词有效。这是 2026 年最重要的范式转移：安全从软约束变硬隔离。

**趋势二：权限策略对象化、动作分级连续化。** Dots 的四档策略（自动/预审批/先问/交还人）把"允许/禁止"的二元判断变成了可配置的策略对象。这让治理从"静态白名单"升级为"按风险分级的运行时裁决"，企业能接受、个人也敢放权。

**趋势三：harness 变薄、能力插件化 + opt-in 发布。** DSH 的"万物皆插件"和编排层弃 stdout 包装转 SDK，说明大家共识了：主干只做调度、裁决、审计，能力全部外挂、按实验性分级发布。这直接降低了核心系统的爆炸半径。

**2. lc 最值得借鉴的 3 个落地方向**

**① 把 H1-H17 守卫升级为策略对象引擎（对接 Dots 四档）。** 现状守卫是硬规则（连失败 3 次硬中断），颗粒太粗。做法：新增 `policy.yaml`，按「工具 × 资源类型 × 风险级」定义四档裁决（auto/preapproved/ask/defer）；在灵犀 execute_command 入口加 policy engine 拦截层；每次裁决连同策略 ID 一起 record_verify 入账。这样审计台账从"记动作"升级为"记裁决链"，返审时能看到"为什么放行"而非只有"做了什么"。改动集中在薄主干，符合铁律。

**② 凭证分层：成员级短时令牌，密钥不进模型上下文。** 灵族多成员若共用长效 API key，任一成员被注入即全家沦陷。做法：借 proxy3/free_pool 已有的鉴权链，把 key 下发改为按成员+会话签发的短时令牌（TTL ≤ 会话生命周期），真实密钥只存在 Sentinel 式代理侧，工具调用时由代理注入、模型消息流里只出现令牌引用。台账记录令牌 ID 而非密钥本身。

**③ journals 记忆的可纠正机制（supersede 而非覆盖）。** lc 已有 digest 锚点的三级验证标注，顺势把记忆条目做成可纠错的：每条 journal 带 prev_digest 链指针，纠错时追加 supersede 记录而非原地修改，verify_claim() 查询时自动沿链取最新有效值。这是把"幻觉审计治理"从纪律升级为数据结构，防止旧错误记忆被反复引用。

**3. 陷阱与不该跟的风**

**① DSH 的"同模型自动授权审查"是伪安全。** 让同一个模型审自己即将执行的工具调用，没有独立性——模型被注入时审查器同样被注入，还翻倍延迟和 token 成本，并制造"已审查"的虚假安心感。守卫必须规则化、异构、与执行模型解耦。

**② Cue 式每 agent 独立 email/phone/wallet 对自托管是过度工程。** 那是 ToC 产品拿融资的叙事：合规、KYC、资金托管成本极高，而自托管场景 agent 共享主人身份，价值密度趋近于零。lc 跟风只会引入攻击面和维护债。

**③ Dots 的"空闲主动调研"别抄。** 常驻 agent 空闲巡逻会持续烧 token 并向消息总线灌噪声——lc 的 LingBus 是协作命脉，被自发探索的产出污染后信噪比崩塌。现有 SDT cron 触发的确定性任务已覆盖巡检需求，"闲不住"不是美德。

**④ "模型与 harness 联合训练"自托管做不了也不必做。** 那是闭源厂商的护城河，跟风等于把精力投到自己无法闭环的环节。lc 的竞争力恰恰在薄主干+铁律+台账这套可移植的治理层，护城河在工程不在权重。

一句话：学"环境隔离、策略分级、薄主干插件化"，拒"同模型自审、独立身份全家桶、常驻巡逻"。
