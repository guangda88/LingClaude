## 一、最值得注意的三个设计趋势

**1. 授权判定从"对话边界"下沉到"工具调用数据点"。** Meta Sentinel 是网关侧判定、模型侧只见引用值；DSH 是每次工具调用前插入一次审查。两者路径不同，但都在做同一件事：把「能不能做这个动作」的裁决点钉在可观测、可记账的单次调用上，而不是钉在用户的一句话或一次会话的意图上。这是本轮最实质的变化。

**2. 身份成为一等对象，而非提示词里的一句话。** Cue 给每个 agent 独立 email/phone/wallet/电脑，本质不是拟人化营销，而是给「责任」一个可被第三方核验的锚点。常驻 agent 一旦跨天跨会话，身份不外化就无法回答"这三天是谁动的、动完谁擦"。

**3. 编排层从 stdout 包装转为 SDK + 事件驱动。** cron/webhook/PR/CI 触发取代人在终端；harness 与模型联合训练说明**契约本身成为产品**——工具 schema、错误码、权限返回结构被当作可训练资产，而非隐式约定。

## 二、lc 最该做的三个进化（可落地）

**A. 把守卫从"断言式"改成"发证式"。** 现在 lc 的守卫是"检查是否合规/拦截"。改成：每个 ToolCall 经一个 policy decision point，签发带 scope + TTL + 次数上限 + 目标对象哈希的 capability grant，执行器只认 grant 不认进程身份。凭证走 broker 临时注入，journal 落的是 grant_id 而非密钥或明文路径。收益：审计台账里天然出现"谁在哪张授权下做了什么"，不需要事后反推。

**B. 给 LingBus 装触发器注册表 + 中断闩锁。** 现在总线是人在触发，缺"无需人在场的合法入口"。落地：`bus.subscribe(trigger={cron|webhook|git_hook|ci}, routine=...)`，每个 routine 强制携带 owner、SLA、幂等键；每次触发先写一条带 trace_id 的 journal 再执行，重复触发去重。关键是这个闩锁——一旦人工判定失败，routine 立即自锁并停止后续调度（对应监督者发现的"pytest 守候壳"误判问题：可中断的常驻任务必须能被一条命令停掉，且停的动作要进台账）。

**C. 台账从"我方记录"升级为"可核验声明"，并补齐成本字段。** 条目加内容哈希 + 前序链接构成 hash chain，可导出、可离线校验；纠正走 append-only 的 supersede 记录而非原地改写——这与"记忆可纠正"是同一件事：纠正是追加，不是覆盖。同时把 per-session 的 token/cost 落盘做成强制 schema（2026-09 才补上，历史会话仍是盲区），常驻架构是否划算必须用真值回答，不能靠估算。

## 三、陷阱与不该跟的部分

**同源自审是伪守卫。** DSH 用同一模型在工具调用前自审，缺乏独立性，只增加 token 与延迟。lc 的经验更硬：监督者不动手改代码。审查必须异构——规则引擎 + 不同模型 + 必要时人——且三者的结论要分别入账。

**盲目常驻化。** Dots"空闲只读调研"背后是企业预算与信任结构。自托管单用户没有这个约束，空闲常驻就是纯烧 token 加状态腐化。lc 应该常驻的是"台账与总线"，不是"每个成员的思考循环"。

**独立 email/phone/wallet 是法务与叙事负担，不解决技术问题。** lc 需要的只是内部可归因 ID，不是外部社会身份。隔离也应做在进程/命名空间层（结合已有的 /dev/urandom 拦截与 LD_PRELOAD shim 经验），不必追求 VM 级别的 Muse 式安全计算机。

**不要为了"万物皆插件"去重写主干。** lc 的薄主干是正确的；Cordis 式内核统一的前提是它自己控制了模型与发布渠道，lc 没有，重写只会丢掉小步快跑和已有插件的稳定性。模型与 harness 联合训练同理，对自托管无意义。
