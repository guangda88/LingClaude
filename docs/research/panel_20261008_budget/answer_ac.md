# 插片征答：会话预算预警与接力恢复（R1/R2/R3）

## Q1（R1：WARN 是否让模型可见）

**裁定：B（升级为模型可见），注入点放 turn 循环，不放 submission 层。**

理由：事故的根因不是「暂停太狠」，而是「模型在 22.7M/20M 之前完全没有收到任何可行动信号」。WARN 只给人看，等于把整个收敛窗口的责任压在人的轮询上——而人不会盯着状态栏。给模型 15% 预算的收敛窗口，是三个 R 里投入产出比最高的。submission 层与 turn 循环的区别是决定性的：submission 层每个请求都拼（工具结果、子请求、重试都算），一条 WARN 注记会在一个长会话里被复制 N 份并反复进 input，本身就是污染源；turn 循环每轮一次，与语义单元对齐。

污染对策（三层，缺一层就会退化成噪音）：
1. **一次性闩锁**：session 级 `warn_injected` 标志，85% 只注入一次，写入后不再重复。
2. **升档再注**：若想二次提醒，用升档而非重复——92% 换一段措辞更强的注记（不同文本，不复用同一段），且仍只一次。
3. **措辞必须非终止性**：写「剩余预算 ~15%，请在下一个自然检查点做一次状态外化（写 todo/检查点），**不要中止任务**」。若措辞含「准备收尾/即将挂起」，模型会在预算充裕时提前半途而废，这是比不告警更坏的失败模式。

最大风险：**假阳性交接标记**。注记里一旦出现「准备交接 / 写 handover」的字样，模型可能主动写 relay 标记，从而触发外部编排器自动开新会话——由一句提示语引发了不可逆的会话迁移，且用户毫无察觉。对策：注记只提「状态外化 / 检查点」（复用 LONGTASK_SOP 的既有产物），**不出现 handover / relay / 接力 等词**；relay 标记的写入权只留给 98% 那一档的白名单轮次。

补充一条实现细节：注入文案必须**指名工具与文件路径**（"把当前任务 todo 写入 <绝对路径>"），不能只说意图。否则模型会在聊天框里说「我已写好交接」而实际没落盘——交接状态又回到内存里，等于白做。

## Q2（R2：PAUSE 时是否放行一次遗言轮）

**裁定：B，但必须重新定义形态——不是「暂停会话再走一轮」，而是「一次预算豁免的、小上下文的交接请求」。**

这是本轮最关键的一处修正。题面事故的数字是 input 22.7M：若按「正常会话再发一轮」实现，这个请求要**重放 22.7M 的完整上下文**才能送达。它有两个致命问题：(a) 成本上再吃一个整轮量级，很可能直接把会话推爆；(b) 更糟的是，它极可能**超过模型单请求的真实上下文上限而直接报错**——也就是说，遗言轮恰好在最需要它的时刻失败。换言之，按字面实现 B，R2 是一个在最需要时失效的机制。

正确形态：在 98% 触发时，**不走原会话续接**，而是发一个独立的小请求，输入仅含（a）任务 todo 清单，（b）最近 N 轮的截断/摘要，（c）固定模板的交接指令。成本量级从「一个满轮」降到「零点几个百分点」，且不依赖原上下文是否装得下。模型在这一轮里被硬指令限定为「写交接文件 + 打 relay 标记，不得继续任务」，产出落盘后立即 PAUSE。

**与红线是否冲突：不冲突，但必须区分两件事。** 「暂停=暂停、恢复权在用户」约束的是**任务是否自动继续**，不是**状态是否被保存**。白名单轮不推进任何任务目标、不修改任何业务文件，恢复权 100% 仍在用户。守界靠两点：白名单轮的写权限收敛到交接产物本身（其余工具在提示层禁掉）；产出经 relay_audit 对账。

**但这里有一个必须提请面板裁决的一致性裂缝**：外部编排器的既有行为是「检测 waiting_relay → 自动开新会话 → 注入 resume_hint」。如果 98% 白名单轮写出的标记与 98% 由用户手动 reset 后自写的标记同形，那么**用户点 /budget reset 的同时编排器已经自动把任务接走了**——恢复权事实上从用户手里滑到了编排器手里，与红线精神冲突。建议：白名单轮写出的标记带 `origin=paused` 字段，编排器对 `origin=paused` 的标记**不自动开新会话**，改为向 LingBus 发一条「现场已保存，待确认」的通知，等用户显式 `/budget resume` 或 `/relay resume`。这条不改则 B 方案实际是在红线背后开了一个自动恢复的口子。

**白名单请求自身失败（超时/超长/5xx）如何兜底**：分三层，且失败必须是**静默降级**而不是重试——
1. 该轮预算豁免、免重试（重试 = 在已经超预算的会话上再叠一次确定性失败）；
2. 失败即直接 PAUSE，并在状态栏显式打「交接未落盘，现场仅存于 transcript」+ 提示 `git status` / transcript 路径，让人知道去捞什么；
3. 真正的兜底防线在更早一层：Q1 的 85% 检查点外化。**只要 85% 那一档模型已把 todo 落盘，遗言轮失败就不是灾难，只是交接摘要质量下降。** 所以 R1 与 R2 不是两个独立功能，R1 是 R2 的降级保险——这个依赖关系应写进设计，不要当成两个可各自否决的选项。

最大风险（次级）：**交接模板与既有 LONGTASK_SOP / todo_log / relay_audit 三套产物各写一份**，形成第三套交接格式，字段不对齐导致 relay_audit 对账误报或漏报。建议 R2 复用既有 LONGTASK_SOP 的状态外置格式，不新造 schema。

## Q3（R3 归属裁定）

**裁定：A + B 组合，A 为目标态、B 为过渡态；C 的降级理由不成立。**

SESSION_CONTEXT 的组装确实在 harness 生成层，治本要走 A，这没有争议。但「等 harness 改」期间，B 的成本极低（本地一个标记文件 + turn 循环里一处闩锁式注入，约几十行），而它覆盖的正是**单人用户最常见的场景**：人看到 PAUSE，不开编排器、不跑命令，直接打一条新消息开新会话。编排器覆盖的是「机器全自动」，C 想砍掉的恰好是「人手动」那半边——而这半边的价值不低。

因此排序：先 B（可独立上线、无外部依赖、当轮就能止住新会话丢现场的漏洞），同时把 A 作为 harness 侧需求提单（附本次事故作为证据），B 的注入逻辑设计成**幂等且可被 A 吸收**——A 落地后 lc 侧钩子退化为「不重复注入」的兜底，不产生双份 hint。

B 的最大风险：**与编排器双注入**。两处都注入 resume_hint → 新会话首轮出现两份同样的注记，且两份的 todo 快照可能不同版本。建议以 `relay_id` 为幂等键，新会话内首次注入即写 latch；注记里带 relay_id，后到者见到同 id 已注入即丢弃。另需注意 B 与 Q1 的措辞纪律同源：注记必须指名路径与工具，不能只说「继续上一个任务」。

## Q4（档位与顺序）

**裁定：档位顺序正确（warn → 交接 → 暂停），两个数字要改，一条会计规则要加。**

1. **98% 这个固定阈值太脆，建议改为自适应触发。** 会话内的单轮消耗差异极大（一次 400K 工具结果 vs 一次 50 token 回复），固定 98% 意味着：轮次大时，98% 到 100% 之间可能只剩**一轮**的余量，交接轮根本挤不进去；轮次小时，98% 远远够用，交接轮纯属多余。判据改为**剩余预算 < P90(本会话近 20 轮的单轮消耗)** 时触发。这样无论轮次大小，交接轮都有 ≥10 轮的头寸。98% 可作为上界兜底（剩余不足 10% 时必触发）。
2. **85% 建议改称「检查点档」而非「告警档」。** 它的真正价值不是提醒模型要收敛，而是**无条件把状态外化一次**——哪怕 PAUSE 从不发生，这份检查点也在。与其指望模型在看到预警后「主动收敛」，不如把 85% 定义为「强制一次状态外化」这一确定动作，后者可验收、可对账，前者依赖模型意愿、不可验收。措辞相应地要写成祈使（"现在写一次检查点"）而不是提示（"你快没预算了"）。
3. **白名单请求的预算会计：豁免、且必须是小上下文。** 见 Q2——按正常轮续接实现的话，它会自己把会话推过 100%，把「救命的最后一轮」变成「压死骆驼的最后一根稻草」。规则写死：**交接轮使用独立小上下文 + 预算豁免 + 免重试**；豁免额度设上限（如 1% 预算或固定 200K input，取小者），超出即放弃交接直接 PAUSE。
4. **补一条现有方案缺失的档位考虑**：`/budget reset` 之后，档位闩锁必须**全部重置**（warn_injected / handover_used）。否则第二次超预算时，85% 不再注入、98% 已被「每进程生命周期一次」用掉——PAUSE 将退化为零交接的裸挂起，比第一次事故更糟。这一条在草案的「每进程生命周期一次」约束里被漏掉了（它假定了一个进程生命周期内只会 PAUSE 一次，但 `/budget reset` 的存在正是为了让它发生第二次）。

最大风险：档位增多后，「哪一档的产物算合格」缺乏单一判据。建议把三个档位的产出收敛到**同一个检查点文件**（含 todo / 下一步 / 现场路径），用 relay_audit 单点对账，而不是每个档位各产各的。

Q2 的小上下文重构与「origin=paused 不自动恢复」的一致性判断，是我最有把握也最想推回面板的一条（事故数字 22.7M/20M 直接支持「满轮续接会失败」这一推断）。置信度扣在两处：一是我未读代码，`/budget reset` 是否真的重置进程生命周期、以及 turn 循环的注入点是否真在 lc 侧可控，都未核实；二是 harness 侧 A 方案的落地时程完全不可控，这直接决定 B 是不是长期方案而不是过渡方案。
