你是外部评审 agent。请针对以下设计问题给出**倾向 + 理由 + 风险**，直接作答（不用读代码库；上下文已给足）。
背景：AI 编程助手灵克（Claude Code 形态）有会话预算闸（WARN 展示层 / PAUSE 硬挂起，fail-open，/budget reset 出口）。
真实事故：长任务会话 input 22.7M/20M 触发 PAUSE 硬挂起——模型没有「遗言轮次」，交接状态只存在内存，任务现场全丢。

## Q1（R1 预告警升级：WARN 是否应让「模型」可见？）
现状：WARN 只进状态栏与 /budget 命令（人可见，模型不可见）。
方案A：维持展示层——人看到后自行决定（reset/调阈值/喊停）。改动零风险。
方案B：升级为模型可见——接近 warn 阈值时，把预警注记拼进下一个模型请求（类似 R8 轮次提示的注入先例），模型会主动收敛（写交接、收尾）。
你的裁定？若选 B：注入点放 submission 层（每个请求拼）还是 turn 循环（每轮一次）？有无「注记反复出现污染上下文」的担忧与对策（如只注入一次/每 N% 升档再注入）？

## Q2（R2 遗言轮：PAUSE 时是否放行一次 handover 白名单请求？）
现状：达 pause 直接挂起，无遗言轮。
方案A：维持现状——恢复权完全在用户（/budget reset），机制最简单，代价是硬挂起必丢现场。
方案B：白名单一次——达 pause 时放行**一个**仅用于交接的请求（模型收到的是「写 handover/relay 标记，不得继续任务」的硬指令），产出落盘后必停。防滥用约束草案：①有激活 relay 标记或 todo 清单才放行；②每进程生命周期一次（/budget reset 不恢复）；③产出经 relay_audit 对账。
你的裁定？方案B 与「暂停=暂停，恢复权在用户」红线是否冲突？白名单请求若也失败（如超时）如何兜底？

## Q3（R3 接力恢复自动化：归属裁定）
新会话自动检测 waiting_relay 并注入 resume_hint——侦察确认 SESSION_CONTEXT 组装在 harness 生成层（lingclaude 源码域外）。
方案A：划归 harness 侧需求（lingclaude 不动）。
方案B：lingclaude 侧做恢复引导钩子（--recover 恢复会话时检测本地 waiting_relay 标记，turn 循环注入 resume_hint）。
方案C：编排器已兜底全自动场景，R3 增量价值仅剩「人手动开新会话」场景，可降级不做。
你的裁定（可组合）？
