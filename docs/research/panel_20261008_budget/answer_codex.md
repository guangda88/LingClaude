# 插片征答：会话预算预警与接力恢复（R1/R2/R3）— 外部评审意见

评审基线：22.7M/20M 触发 PAUSE、交接态只在内存 = 事故根因不是"闸太严"，而是**闸把"停止"等同于"抹除现场"**。因此三条裁定都应朝同一原则收敛：**中止语义 ≠ 丢失语义**。凡是不能在无人工介入情况下自动把现场写出去的闸，都是 fail-open 逻辑上的隐性 fail-closed。

---

## Q1（R1 预告警：WARN 是否模型可见）

**裁定：B（模型可见），但采用"单次注记 + 阶梯升档"，注入点放 turn 循环（每轮一次评估），不放在 submission 层逐请求拼接。**

理由：

1. WARN 的价值归属错配了。当前 WARN 只有人可见，意味着"预警"实际是**事后通知**——它通知的是那个无法改变结果的对象。人在会话进行中看到 85% 状态栏，多半来不及、也不具备判断"现在该收尾"的上下文；而模型是唯一知道"我还剩三步没写盘"的角色。R8 轮次提示已有注入先例，机制与心智模型都是现成的。
2. 注入点选 turn 循环而非 submission 层。submission 是"每个请求都拼"，会出现同一会话内 N 个请求携带同一注记，在长任务里 N 很大（工具调用密集时一 turn 多请求），是上下文放大与污染的主要来源。turn 循环天然给出"每个语义轮次至多一次"的节流，且能拿到 turn 级状态（当前 turn 起点 usage、是否已收尾），实现上更容易做幂等。
3. "反复出现污染"这个担忧成立但可用计数消解，不必退让回 A。核心不是"注记出现几次"而是"每一条是否携带新信息"。单调重复的注记会挤占 attention 并让模型学会忽略它（ignored-instruction 衰减），这才是真风险。

对策（建议的最小实现约束）：

- **一次性**：`warn_notified` 幂等位，同一进程生命周期内 85% 只注入一次。
- **阶梯升档**：85% 一次；再涨到 ~93% 允许第二次（措辞升级为"即将硬挂起，请立即落盘"）。**最多两次**，此后不再注入。
- **升级判据**必须基于**预测**而非当前值：如果"按本 turn 趋势再一个 turn 就会破 pause"，直接跳到强措辞。事故场景 22.7M/20M 是典型的"跨 turn 突然爆"，事后阈值毫无意义。
- **注记位置**：放在 turn 循环注入的系统/提醒段尾部，并带明确的**作用域**标记（`[budget-warn, session-scoped]`），让模型知道这是环境信号而非任务需求。
- **语义纪律**：注记只要求"收敛与落盘"，**不得**要求模型调整任务范围或自行改阈值——否则 WARN 变成模型侧的行为操纵面。
- 达到 85% 后可**主动允许模型收敛**：把"注记"升级为"权限收缩"（禁止发起新的探索性调用，只允许写文件/写 handover），这比纯提示更可靠。

**最大风险**：注记成为可被任务内容"解释掉"的软信号。模型在长任务里读到 85% 提示后，可能判定"这个任务本来就快结束了"而继续展开，反而加速撞线。缓解手段是让注记**同时**带不可辩驳的机器事实（`used/total、距离硬挂起剩余 turn 估算、PAUSE 后不可自动恢复`），并把 98% 档作为不依赖模型配合的兜底（见 Q2）。另：WARN 档若注记本身消耗 token，收益是负的——因此必须"一次性 + 短句（≤40 token）"。

## Q2（R2 遗言轮：PAUSE 时白名单放行一次 handover 请求）

**裁定：B（白名单一次），并且我认为它不与"暂停=暂停，恢复权在用户"红线冲突——因为它改变的不是"是否暂停"，而是"暂停时的状态持久化"；但需要把红线重述清楚，否则未来会被人拿来当先例打穿。**

红线的精确表述应当是：**PAUSE 是"任务推进"的硬停，不是"信息写入"的硬停。** 用户拥有的是"何时继续执行任务"的决定权；系统保留的是"把当前状态完整写盘"的义务。遗言轮不推进任务（硬指令禁止继续任务），不产生新的工作产出，只把已经在模型上下文里的状态外化。任何"恢复权在用户"的红线如果被读成"PAUSE 后系统不得有任何动作"，那事故就会以 100% 的概率复现——所以这条红线本身需要这次修订。

三条防滥用约束的裁定：

- ①（有 relay 标记或 todo 清单才放行）：**支持，但 todo 单独不够**。事故场景很可能就是"没有 relay 标记、但有正在跑的修改"。todo 存在只是"有现场"的弱信号。真正的门禁应是**有未落盘风险**——例如 git status 非干净、turn 中途被打断、存在 `.tmp`/未提交改动。todo 只能作为"为什么值得写"的判据之一。
- ②（每进程生命周期一次，`/budget reset` 不恢复）：**这条最重要，保留，并且要写死为不可绕过**。但注意一个漏洞：用户可以靠"多开进程"重置这条计数，而这正是编排器要接管的场景——所以单实例约束应由**进程 + 会话双重计数**（`/budget reset` 不清空会话级 handover_used 标记，只有显式新会话才清）。这是最容易被未来"优化"掉的一行代码。
- ③（relay_audit 对账）：支持，但把它定位为**观测/告警**而非准入条件。若审计失败阻断遗言轮，就重演"审计组件故障 → 现场丢失"，方向反了。

额外建议的两条：

- **遗言轮必须是可降级的、且有独立预算**。它不能因为"预算已超"而被闸层自身拒绝（否则等于没有）。要预留一小笔应急额度或用非会话通道（本地落盘工具/系统命令）完成交接。
- **交接产出必须是结构化文件，不是自由文本**。事故的痛点是不可恢复；自由文本 handover 的可解析性远低于固定 schema（`当前阶段 / 已完成 / 未完成 / 改动文件与状态 / 可执行的下一步 / 关键文件路径`）。

**白名单请求自身失败的兜底**（草案未覆盖，是我认为必须补的一条）：按可靠性从高到低降级——

1. 一级：正常模型请求产出 handover。
2. 二级：超时/失败 → **不做重试**（预算已超，重试=烧预算），直接用**本地确定性快照**兜底：会话消息尾部 N 条 + git status/diff 摘要 + 最近触碰的文件列表，由 harness 侧脚本落盘成 `handover_fallback.md`。快照质量不如模型总结，但足以让人（或编排器）判断现场，**远好过归零**。
3. 三级：连快照也写不动（磁盘/权限）→ 至少把标记 + 可见状态行写进一个**已知可写路径**（如 /tmp），并在 PAUSE 时向 LingBus/状态栏报警"交接落盘失败"，把失败显式化。
4. 任何一级都必须在 PAUSE 返回里带 `handover_status: ok|fallback|failed`，让上层编排器知道该等文件还是该告警。

**最大风险**：把"遗言轮"演化成事实上的第二段任务执行。模型完全可能在硬指令下"顺手"多做一步（改一个文件、跑一个命令）。缓解：白名单请求在请求构造层**禁用写工具/命令工具**（只允许文本 + 固定的 handover 写文件工具），而不是仅靠提示词约束——提示词约束在这类临界状态下最不可靠。

## Q3（R3 接力恢复自动化：归属裁定）

**裁定：B 为主 + C 为兜底 + 明确 A 的边界。组合执行。**

- **B（lingclaude 侧 `--recover` 恢复钩子）**：支持，且优先于 A。理由是这次事故的失效点有两处，只修后半段不够：闸把现场丢了（Q2），新会话又得靠人去想起来。`--recover` 属于**进程内、零 harness 改动、可独立灰度**的范围，改动面与 R1/R2 同级，收益是把"人手动开新会话"这一残余场景从"靠记忆"变成"靠标记"。
- **C（降级不做全自动）**：同意其作为**边界**而不是替代。"编排器已兜底全自动"这条推理成立，但它兜的是**系统自己开的会话**。对于用户手动 Ctrl-C / 关终端 / 换客户端开的会话，编排器无从介入。把 C 当"因此 R3 价值仅剩手動场景"进而整体降级，逻辑上不成立——手工场景恰恰是当前唯一有洞的场景。
- **A（划归 harness）的边界**：只有当需求升级为"**默认无参启动**也要自动注入"时，才必须落到 harness 的 SESSION_CONTEXT 组装层。侦察结论（组装在 harness 生成层）是对的，但**不要把 R3 整个判给 harness**：因为 harness 侧改动依赖 lingclaude 之外的责任方排期，事故复发的等待成本远高于收益。

具体建议的分工：
- lingclaude 侧现在做：写 `waiting_relay` 标记（由 Q2 遗言轮产生）、`--recover` 检测 + turn 循环注入 resume_hint、resume 幂等与重放保护。
- 上报/推动（不阻塞）：把 resume_hint 注入点写进 harness 侧需求单，作为无参启动的长期形态。文档先行，等排期。

**最大风险**：`--recover` 变成新的"猜测来源"——在新会话里注入了一份**过期**的 resume_hint（现场已被另一条路径处理过），模型对着不存在的现场继续干，产生比"什么都不做"更糟的二次破坏。对策：(a) `waiting_relay` 标记带 `session_id + created_at + handover 文件路径 + 状态位`，resume 消费后**立即置为 consumed 并落日志**；(b) `--recover` 必须在首轮**显示**注入内容并要求确认（人在环），不做静默自动；(c) 标记与 handover 文件的 mtime 差超过阈值时降级为"仅提示存在现场，请人工确认"。

## Q4（档位与顺序）

**裁定：档位顺序（85 → 98 → 100）正确，不动；阈值 85% 建议下调、98% 建议上调；白名单请求的预算必须豁免。**

逐项修正意见：

1. **85% WARN：下调到 70%–75%。** 理由是延迟余量不对称。WARN 到 PAUSE 之间只有 15% 的空间，而事故现场 22.7M/20M 说明一个长 turn 就能吃掉 15% 以上（22.7M 相对 20M 即 +13.5%）。**阈值应按"至少还能跑两个 turn"来定，而不是按"离上限还有多远"来定。** 建议 75%，或更稳的做法：阈值不写死百分比，而是 `min(75%, 上次同类 turn 平均增量的 2 倍余量)`。
2. **98% ONE_SHOT_HANDOVER：上调到 90%–92%，或改为"剩余 1–2 个 turn 预算"触发。** 98% 留给遗言轮的窗口太窄：模型发起请求到 PAUSE 可能只隔一个 turn，注记型提醒在这种情况下根本来不及生效——它需要**一个完整的 turn**来做交接。触发判据建议从"百分比"改为"**按 turn 预测的剩余预算**"：若"再一个 turn 就会越线"，直接进 handover 档。这一条比数字本身重要得多。
3. **档位顺序正确，且应保持单调递增不可跳过。** 85/98/100 的语义是"提示 → 强制落盘 → 硬停"，逻辑链完整，无需重排。
4. **白名单请求自身消耗：强烈建议豁免出预算核算（或走独立应急额度）。** 这是本节最关键的一条。理由：白名单请求的唯一存在意义就是"在预算耗尽时把现场写出去"，如果它自己还要排队等预算，结果是**遗言轮永远在最需要的时候最拿不到**，设计自毁。同时它必须**不计入**后续 WARN/Pause 档位的分母，否则会引发连锁判定（写完交接后立刻因"超额"再进 PAUSE，语义混乱）。建议实现上给 handover 通道一个 `budget_exempt=true` 标志，并单独计入 relay_audit 的用量账而不计入主闸。
5. **补充一个未在拟议中的档位：`fail-soft PAUSE`。** 即 100% 时若 handover 已被消费过（Q2 约束②）或系统判定"现场已安全落盘"，PAUSE 应当允许**只读**请求继续（供用户查询），仅禁写。当前 fail-open 语义下这两者被混为一谈，会让用户在 PAUSE 后连"到底进行到哪了"都问不出来。
6. 补充：`/budget reset` 之外，应给 `/budget handover` 手动触发口，让用户在**预算未耗尽**时也能主动收尾落盘（预防性交接），复用同一套白名单机制。这比所有阈值调优都更实用。
