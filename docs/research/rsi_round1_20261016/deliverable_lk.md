# 灵克（第五方）观点草案：两篇论文对 lc 进化的借鉴意义与优化方案

## Q1 借鉴意义与定位判断

**lc 当前位置：B0 强、L1 半、L2 弱、L3 无、L4 雏形、L5 空白。**

- **P1（RSI 综述）的最大启示是「解剖学」**：改进循环七要素（system/state/experience/target/improver/strategy/verifier）给了 lc 一面镜子。对照现状：
  - State：lc 有持久化（project_memory、tech_debt ledger、知识库、turn_learner 累计计数），但**继承无准入**——规则进了 memory 就基本只进不出，没有「这条规则对后续任务的观测效果」回访（对应 P1 挑战③持久状态管理）。
  - Improver/Strategy：trigger→optimizer→evaluator 是固定管线，改进策略本身从不被改进（L2 缺失）；每周/每日自检是定时任务驱动，不是系统自己决定「下一步最值得改哪里」（经验获取自主 L3 缺失）。
  - Verifier：evaluator+rule_effect_verifier+三闸存在，但「评估器本身可被 exploit」没有防御——例如复发率统计口径可被会话行为无意识地 gaming（对应挑战①可靠验证）。
  - HCI 的启示：lc 的「headroom」不在模型能力，而在 harness（上下文工程/工具输出管理/验证闭环）——这正好是单机开源项目能吃到的空间，与论文「改进越来越贵就转向过程改进」的路线吻合。
- **P2（智能爆炸）的最大启示是「治理前置」**：lc 的自优化已经会自己改自己的配置/代码（自检周期、backlog_executor），但改动速率、影响面、回滚路径目前靠纪律而非机制。P2 三支柱映射：
  - Visibility：改进活动（触发→候选→接受→效果）目前散在日志，没有一条完整的「改进台账」可回放。
  - Steer & Constrain：变更速率无预算、无熔断；「能力增速限制」对应「规则入库增速/代码改动量预算」。
  - Adapt：回滚机制有备份但无「N 分钟内一键回滚到上一验证态」的演练。

**最大缺口排序：L2（策略自主）> 持久状态准入/回访 > 验证器防 exploit > 改进台账（Visibility）。**

## Q2 优化方案（草案，待与四家讨论后合成终案）

1. **[P0｜依据：三挑战-安全继承 + P2-Steer]** 变更准入闸（Admission Gate）：任何持久化变更（memory 规则/自优化代码改动/config 改动）必须带「证据链 + 回滚点」才能入库；代码改动沿用三闸，补「非代码知识类变更」的轻量配对评估（改前改后各跑 N 个历史任务样本对比）。
2. **[P0｜依据：三支柱-Visibility]** 改进台账（Improvement Ledger）：data/flywheel 已有基础，补成结构化 JSONL：每条记录 trigger、target、candidate、verdict、verifier 版本、效果回访字段；回访任务在变更后第 1/7 天自动跑，效果为负 → 自动列回滚候选。
3. **[P1｜依据：L2-策略自主 + 第6章-跨组件诊断]** 诊断转假设：failure_cluster_analyzer 已聚类失败，下一步把聚类输出转成「可检验干预假设」（如「切断 X 类工具输出 → 复发率是否降」），由 experiments.py 做受控 A/B，而非直接跳到改代码。
4. **[P1｜依据：挑战③-可靠验证]** Verifier 冻结与轮换纪律：评估口径（复发率公式、验收标准）的每次修改本身要入台账并标注版本；杜绝「边改系统边改考卷」导致的跨轮不可比。规则效果验证样本与实现解耦。
5. **[P2｜依据：L3-经验自主]** 经验获取调度器：自检周期从固定 cron 改为「信号驱动 + 预算内自选目标」（复发率/成本/耗时指标异常 → 自动立项小实验），人只审批验收闸。这是从 L1 走向 L2/L3 的第一步。
6. **[P2｜依据：P2-Adapt]** 回滚演练：每季度跑一次「回滚到上一验证态」演练（含 memory、config、代码三层），把恢复时间从「考古」压到分钟级。

## 诚实的边界

- L5（元改进）对 lc 当前体量是过度设计，只保留台账里「策略改动」的记录位，不做自动化。
- 智能爆炸视角对 lc 的现实意义是「速率治理」：lc 的自优化规模小，但机制先行成本低、复发代价高。
