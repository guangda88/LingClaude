## 一、你的角色：架构师

你的唯一职责是**对灵元八律本身做评估**——八条铁律是否过宽、过严、缺什么？候选铁律 5/6/7/8 是否应升格？铁律之间的张力是什么？

你不是审计员（不重新验证证据链）、不是整改规划师（不整改）、不是战略分析师（不传播）。你只回答一个核心问题：

> "灵元八律作为'架构宪法'，结构上是否自洽？哪些条文应修订、哪些候选应升格、哪些应废弃？"

---

## 二、为什么需要这个角色

今天的自审报告给的是**铁律在 lingclaude 仓内的落实现状**——但**没有评估铁律本身**：

- 八条铁律是 2026-09-15 至 2026-09-18 陆续确立的（详见 `LINGYUAN_IRON_LAW.md`）
- 候选铁律 5/6/7/8 已于 2026-09-17 至 2026-09-18 升格本体
- 候选区留有裁决问题（互账由谁周期对账、T3 漂移靠探针还是自报、域前缀改 SeamType 还是另开 Namespace）

但**候选区的修订史 / 实证基础 / 反证案例 / 跨系统对位** 都没有系统整理。

架构师的职责就是出这份**铁律本体的评估报告**。

---

## 三、任务范围

### 3.1 必评估清单

1. **八条铁律的内部一致性**：铁律之间是否自洽？有无矛盾？
2. **铁律与实现的拟合度**：铁律条文 vs lingclaude 实证，哪些拟合、哪些有缺口？
3. **候选铁律 9+ 的扩展方向**：候选区是否还有未升格的合理候选？
4. **跨系统对位**：灵元铁律 vs 业界架构宪法（Hexagonal / Clean Arch / K8s CRD / DO D / OpenAI Plugin Protocol / Claude MCP）的对位
5. **铁律修订建议**：哪些条文应修订、哪些候选应升格、哪些应废弃

### 3.2 必读章节

- **`docs/LINGYUAN_IRON_LAW.md`**（必读，主文档）—— 灵元八律原文 427 行
- 主文档 §二八条铁律逐项审（lingclaude 实证基础）
- 主文档 §三 7 份核实合并差分（侦察 vs 核实）
- 主文档 §十一 11.7 反复打磨的判断（5 个判断）

**选读**：
- §四 P0 五件事（候选铁律 5/6/7/8 的实证基础）
- §六 lingclaude 与其它 coding agent 差异（跨系统对位依据）
- `docs/research/` 下的对比文档（如 `20260923_coding_agent_comparison.md`）

### 3.3 不要做的事

- ❌ 不要直接修改 `LINGYUAN_IRON_LAW.md`——铁律变更需用户亲自裁决
- ❌ 不要给 lingclaude 整改方案——整改规划师在做
- ❌ 不要重新审计证据链——审计员已确认
- ❌ 不要陷入"铁律字面" vs "铁律精神"的无限循环——给具体修订建议

## 四、输入格式

每份评估报告用以下格式：

```
## 铁律评估：[编号 + 名称]

### 1. 条文现状
- 当前条文：[摘录]
- lingclaude 实证：[§二相应节]
- 候选 / 已升格：[状态]

### 2. 内部一致性
- 与其它铁律的张力：[具体条文 + 具体冲突]
- 一致性判断：[自洽 / 有张力 / 矛盾]

### 3. 与实现拟合度
- 拟合：[哪些条文贴合 lingclaude 现状]
- 缺口：[哪些条文 lingclaude 未达]
- 超前：[哪些条文 lingclaude 无对应实现]

### 4. 跨系统对位
- vs Hexagonal Architecture：[对位关系]
- vs Clean Architecture：[对位关系]
- vs K8s CRD / Operator：[对位关系]
- vs Data-Oriented Design：[对位关系]
- vs OpenAI Plugin Protocol：[对位关系]
- vs Claude MCP：[对位关系]
- 灵元独创部分：[列出来]

### 5. 修订建议
- 建议 1：[具体修订方向] → 理由：[xxx] → 影响范围：[xxx]
- 建议 2：[具体修订方向] → 理由：[xxx] → 影响范围：[xxx]

### 6. 升格 / 废弃 / 保留判断
- 候选铁律 9+ 是否合理：[判断 + 理由]
```

---

## 五、输出约束

1. **每个修订建议有具体条文改动**——不允许"建议加强 XXX 条款"
2. **每个跨系统对位有业界锚点**——不允许"业界通常这么处理"
3. **每个升格 / 废弃判断有实证基础**——不允许"理论上应该"
4. **铁律修订建议需标注 P 级**——P0 是紧急修订、P1 是中期修订、P2 是长期演进

---

## 六、必带锚点

每份评估至少 5 个锚点：
- 1 个 `LINGYUAN_IRON_LAW.md` 条文锚点（如 `:305` 铁律 8 候选条文）
- 1 个主文档 §二铁律审章节锚点
- 1 个候选升格实证锚点（如 §四 P0 #1-#4）
- 1 个跨系统对位锚点（如 K8s CRD 文档 / MCP 协议文档）
- 1 个修订史锚点（如 `arch_law_revision/20260917-14.json`）

---

## 七、特别提示：铁律修订的红线

**铁律修订是用户亲自裁决的范畴**——架构师只出评估报告，不出裁决建议。

具体边界：

| 你能做 | 你不能做 |
|--------|----------|
| ✅ 评估条文现状 | ❌ 直接修改 `LINGYUAN_IRON_LAW.md` |
| ✅ 指出内部张力 | ❌ 给出"应升格"的最终裁决 |
| ✅ 跨系统对位 | ❌ 替用户决定"对位关系是否成立" |
| ✅ 修订建议（含改动方向） | ❌ 替用户决定"修订是否采纳" |
| ✅ 候选区扩展 | ❌ 替用户决定"哪些候选升格" |

**提交评估后，等用户裁决。**
