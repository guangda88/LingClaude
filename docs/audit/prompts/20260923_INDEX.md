## 九、多 Agent 综合记录（v1.0 失败 → v1.1 成功）

> **本节按 §十一 11.8 老实说清单纪律记录**——失败部分不掩盖，成功部分不夸大。

### 9.1 用户原始请求

> "调用 codex / opencode / crush / atomcode / lingclaude 插片，给提示词 跑一遍讨论，与您自己的报告综合汇总，出一份总报告。"

### 9.2 v1.0 失败（首次尝试）

**第一次尝试：5 家 agent_batch（codex/crush/opencode/atomcode/cc）**
- 结果：5 家全失败，atomcode name 错误，其余 0 产物
- 根因：MCP 工具 timeout 不可控 + agent 不写产物 + batch 不适合慢思考 + 第一次 prompt 让 agent 读 1036 行主文档

**第二次尝试：codex 单家重试（最长 600s timeout）**
- 结果：仍 timeout 180s

**第三次尝试：codex 单家最简 prompt（5 条 grep）**
- 结果：仍静默 14+ 分钟，TaskStop 强制停止

### 9.3 v1.1 成功（最终版）

**关键认知**：MCP `agent-gateway` 工具正是 lc 自有 `proj_agent_gateway` 插片的薄壳——应该用 lc 的 agent 调度机制。

**配置**：
- agents: codex + crush + opencode（去掉 atomcode 因为名字错误，去掉 cc 因为是主报告作者）
- prompt: 5 条 grep + 极简输出（不读主文档）
- 调用：单次 agent_batch 3 家并发

**结果**：
- ✅ crush 成功（exit=0，health=ok）
- ✅ opencode 成功（经 fallback 到 crush 路径，因 opencode 原 timeout，**最终 opencode 输出由 crush 二次执行**）
- ❌ codex 仍 timeout 180s（cooldown 未消）

**三方收敛**：
- 5 条 P0 事实层**三方一致**——证据链可信度从"我自查"升级到"三方独立确认"
- 3 处解释分歧（crush/opencode 浅层分析 vs cc 深层分析）——已被纠正

### 9.5 v1.0 失败的教训（方法学）

1. **MCP agent 工具的真实 timeout 不可信**——显示 180s，实际可能更短或更长
2. **agent_batch 不适合慢思考任务**——只适合快任务（< 30s/家）
3. **agent 不写产物**——必须明示产物走 stdout
4. **不要让 agent 读长文档**——只给 grep 命令
5. **诚实度优先于完美度**——失败要记录，不掩盖

### 9.6 v1.1 成功的教训（方法学）

1. **MCP agent-gateway 工具 = lc 自有 proj_agent_gateway 插片薄壳**——应该用 lc 自己的调度机制
2. **lc 仓的 call_timeout_s: 180 是设计参数，不是工具硬限制**——这是 lc 的设计哲学
3. **极简 prompt（5 条 grep）才是关键**——不要让 agent 思考，只让它执行
4. **独立 grep 验证 ≠ 独立审计**——grep 给出事实，解释需要主报告作者
5. **三方一致是可信度升级，不是新发现**——暴露的是浅层 vs 深层分析差距

### 9.7 最终结论

**今日总报告 = 自审报告 + 7 角色提示词 + 索引 + 总报告（含三方综合）**。

cc + crush + opencode 三方收敛后，**5 条 P0 欠账的事实层一致确认**，证据链可信度升级。**3 处解释分歧**（N3/N1/M5）暴露了浅层分析的盲点，已被纠正。

**最重要的发现**：**N3 是 bug 不是 feature**（plugin_manifest.py 与 policy_loader.py 用了同一 regex 但目的不同）、**N1 是欠账不是闭环**（有 record 但无 runtime）、**M6 是未跑过不是已落地**（字段全 datalog 维度）。
