## 二、pipeline 依赖链

```
主自审报告（事实层）
    ↓
通用派单提示词（入口）
    ↓
    ├──→ 审计员 ──→ 整改规划师 ──→ 战略分析师 ──→ 诚实审查员   ← 主链（验证→规划→传播→审查）
    ├──→ 架构师 ──→ 跨系统对标员                               ← 旁链（铁律评估→业界对位）
    └──→ 多 Agent 协调员 ──→ 战略分析师                        ← 支线（协议草案→影响传播）
```

**边界纪律**（INDEX §三"不做的事"列）：
- 每个角色严格限定在"自己职责层"，**不越层**（审计员不改代码、规划师不写代码、战略分析师不重定位）。
- 角色产出可直接交给下一环：审计员验证后 → 规划师才敢规划；整改完成后 → 战略分析师才定传播时机。

## 三、使用优先级（INDEX §四：按"何时用"）

| 阶段 | 用谁 | 产出 |
|------|------|------|
| 第一轮：自审 | （已完成） | 主自审报告 |

| 传播材料出来后 | 诚实审查员 | 红线审查报告 |

## 四、本次实际落地的观察

- 这 7 个角色**不是 7 个独立 agent 并行干活**，而是**同一个 agent 在提示词里切换视角**（PROMPT.md §2.1 "可选角色（挑一个或自定）"）。
- 每个 ROLE 文件有统一骨架：角色定义 → 为什么需要 → 任务范围（含必审清单+不做的事）→ 输入格式 → 输出约束 → 必读章节 → 必带锚点 → 与其它角色边界 → 版本说明。
- **核心设计意图**：把"自审"这种一次性任务，变成"可复用、可派单、可校验"的角色化流程——这正是 lingclaude "架构宪法落地"理念在文档层的延伸。
- 我的本次任务（逐行核查 + 修正 + 提交 + 计划 + 开工）实际上**跨了多个角色**：审计员（核查证据链）+ 整改规划师（制订计划）+ 实施者（第一批整改）。
