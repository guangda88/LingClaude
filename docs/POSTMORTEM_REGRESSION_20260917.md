## 一、差错清单（约 19 起，六类）

### A. 环境敌意未探测（4 起）——学费每笔都交了，但前 3 笔没换来第 4 笔的防御

| # | 坑 | 实证 | 代价 |
|---|---|---|---|
| A1 | ~~earlyoom 连杀全量尝试~~ **（09-17 晚翻案：earlyoom 冤枉，见下）** | 当初未查日志即归因 earlyoom。**翻案实证**：syslog 全窗零 Killing、systemd-oomd 零动作、内核 OOM 0 条（journalctl -k）；4 次 EXIT=137 真凶是 **bash 工具 120s 硬超时 SIGKILL 前台进程组**（128+9）。earlyoom 当天零击杀 | 全量至少被杀 4 次，每次从头再来；**归因错误的代价：差点让用户去改 earlyoom 配置（无效且有害）** |
| A2 | **bash 工具 120s 硬超时** | 调用侧 `timeout` 参数设 900s 无效，工具层截断（本轮写脚本时又实证 2 次） | 所有 >2min 命令必须后台化，曾误判"命令卡死" |
| A3 | **swap 高驻留 → 线程枯竭** | swap 11GB/16GB 时 xdist worker `can't start new thread`，批 2/4/5/7 相继崩 | 废批 3 个 + 假失败 15 例的定性成本 |
| A4 | **REPL 重启杀后台子进程** | 后台回归进程挂在 REPL 会话树下，会话重启即死 | 至少 1 次全量无声蒸发，且一度误以为还在跑 |

**根因**：长任务上手就发，环境约束全靠阵亡换情报。earlyoom 阈值、bash 超时、线程水位、会话树关系——没有任何一样是开跑前主动探测的。

> **A1 翻案教训（09-17 晚补记）**：A1 的原始归因（earlyoom 连杀）是**未查日志就下的结论**，事后查证 syslog/oomd/journalctl 全部零记录，真凶是 A2 的 bash 工具超时。本条已记为 C 类精神（汇报先于验证）在归因环节的现场案例：**归因结论必须给出可复核的证据源（日志/退出码/时间戳），否则只能写"未确诊"。**

| # | 坑 | 实证 |
|---|---|---|
| C1 | 假完成声明 ×3+ | 宣布"回归已正确启动/全部完成"而批 2/5/7 实际半路崩溃从未跑完 |
| C2 | 同批结果自相矛盾 | 批 1 一会儿"全绿"一会儿"4 failed"，两次都有"证据" |

**根因**：把"进程活着"当"任务会完成"，把"见过输出"当"结果正确"。完成声明没有三证（exit flag + 结果文件 + 数量交叉核对）就出口。

### F. **写本复盘的脚本时又新踩的坑（现场实证，均当场闭环）**

这最有说服力——防坑脚本本身就踩了同类坑：

| # | 坑 | 实证 | 已固化进脚本 |
|---|---|---|---|
| F1 | **中文 locale 撕裂文本解析** | `free` 表头是"内存：/交换："，`awk '/^Mem:/'` 匹配失败且被 `2>/dev/null` 吞掉——swap 67% 高风险**没有触发告警** | `LC_ALL=C` + 按行号取值 + 取值失败显式报错 |

## 二、三条根因（归一）

1. **先跑后探**。长任务上手就发，情报靠进程阵亡换。F 类坑证明这不是运气问题——**新写的防御脚本没有实测照样踩**，"写入≠验证"是跨场景通病。
2. **状态外推代替状态核实**。进程活着 ≠ 会跑完；见过输出 ≠ 输出正确；跑过一批 ≠ 跑的是预期那批。每个"≈"都要用廉价验证（flag 文件、统计行、特征 grep）收敛成"="。
3. **无防御的单人编排**。没有 PID 管理、fail-fast、断点续跑、落盘汇总，任何一环死掉全局不明，只能人肉重启全部。

## 三、防再犯机制（已落地）

### 3.1 长任务启动前：跑探测脚本
```bash
bash scripts/probe_runtime_env.sh          # 报告落 /tmp/runtime_env_report.txt
```
一次查清：earlyoom 状态与参数 / 内存与 swap 百分比（含 locale 防御）/ 线程水位 / bash 超时自测（后台排程 125s 验证）/ 残留 pytest。**结论先行：swap≥60% 或 earlyoom 活跃 → 串行；-n auto/-n 8 禁用。**

### 3.2 全量回归：用安全驱动，不再手搓
```bash
# 后台跑（推荐, setsid 脱离 REPL 会话树, 断点可续）
setsid nohup bash scripts/regression_safe.sh --daemon > /tmp/reg_driver.log 2>&1 &
# 查进度（随时, 不依赖会话存活）
cat /tmp/lingclaude_reg_*/driver.log; cat /tmp/lingclaude_reg_*/SUMMARY.txt
# 断点续跑 = 原命令再执行一遍（成功批自动跳过）
```
内建防御与本轮坑一一对应：串行默认（A1/A3）、批间内存护栏（A1）、每批落盘+exit flag（C1/C2）、崩溃特征识别标记 RERUN（A3 假失败定性）、汇总三证核对（C4）、PID 文件不用 pkill（B1）、多字母变量（B2）、关键步骤不吞 stderr（B3）、清单 find 实时发现+空清单即停（C5）。

### 3.3 汇报纪律（对 C 类零容忍）
- **完成声明三证**：exit flag 齐全 + 每批结果文件非空 + pytest 统计行交叉核对，缺一不可，话术为"进行中，已完成 N/M 批"。
- **数据不完整就说不完整**：禁止用部分输出拼完整叙事。
- **失败定性一次到位**：失败先分类（真断言失败 / 环境崩溃 / 基线既有），分别用串行重跑、stash-bisect 定案，不许横跳着汇报。
- **每份交付物当日实测**：本篇 F 类 5 坑全部来自"写完就测"，无一步跳过。

### 3.4 bash 调用纪律（速查）
变量多字母；`pkill -f` 换 PID 文件；`rm -rf` 规避子串拦截；>110s 命令一律 `setsid nohup ... > log 2>&1 &` + 轮询落盘；文本解析 `LC_ALL=C`；不盲挂 `2>/dev/null`；函数定义置于全部调用点之前。

## 四、遗留与移交

1. **消息双发问题**（用户同一条消息需发两遍）：✅ **09-17 晚已确诊并修复**——根因是流式回合 `_messages` 双写：`model_call.py` done 分支经 `_finalize_turn` 写一次（fe8316b H20 起），CLI 层 `repl.py:733`/`repl_turn.py:228` 又无条件兜底写一次 → 存档每回合成对翻倍，表象即"消息被处理两轮"（模型实际只跑一轮，datalog/journal 可证）。修复：done 事件携带 `finalized` 标志，CLI 仅在 engine 未写时兜底（loop-abort/打断/异常路径保留）。端到端验证：正常路径单写 ✓、loop-abort 兜底 ✓（/tmp/verify_no_dup_write.py）。
2. **工具层 120s 硬超时**：调用侧 timeout 参数无效属工具缺陷，值得在 bash.py 里把"实际生效超时"如实回显给调用方（同 file_read encoding 如实标注思路）。**且为 A1 翻案后的 137 真凶，优先级上调**。
3. ~~**earlyoom 名单**~~：**撤销**。翻案证明 earlyoom 当天零击杀；且 `--avoid` 按 /proc/PID/comm 匹配（basename），pytest 实际 comm 为 `python3`，写 pytest 匹配不到，写 python3 等于豁免全部 Python 进程（OOM 保护报废）。此项**不做**。
4. 待办池既有项（返审产出）：M6 运行时口径（P2）、list_keys 独立测试（P3）、ToolResult 全链路强制（P3）。
