## 一、铁律本体

### 铁律 1：薄主干——主干是状态机，不是行数

**主干 = 2T3A 的状态机主架构**（records / events / transition 三原语），
对标 DSH 的 cordis 微内核，但**比它更薄**。

- 主干的唯一职责：状态的原语存取 + 插片的装配与调度。
- **一切模块——包括必须的核心模块（provider / tool / sandbox / 治理 / 自优化）——都是可变插片**，注册即生效（`register` / `unregister` 热拔插），拔除后主干继续运转。
- **行数永远不是主干厚薄的度量**。插片在主干上长得越多，代码行数自然越多——这不违背薄主干；违背薄主干的是把"变化"焊进主干，不是代码变多。

> 反例记忆：任何"砍行数 = 架构进步"的提法都是误判。判断对象永远是
> **变化的模块有没有走接缝（type 注册）**，而不是目录瘦了多少。

**薄的定义（2026-09-17 用户确认补充）**："薄"以三重封闭性定义，以行为测试终审：

- **概念封闭**：主干代码（core/）不出现任何插片/业务领域的概念词汇；
- **知识封闭**：主干与装配器代码不含对任何具体 SeamType/插片枚举值的特判分支；
- **依赖封闭**：core/ 的传递 import 闭包 ⊆ {stdlib, 状态机原语依赖}，不得指向 plugins/、engine/ 具体实现（含 lazy import）。

"主干是不是够薄？还能不能再砍？"的机械化答案：**换域测试 + 截肢测试双绿即已最薄**——
再砍任何东西这两个测试就会红；未达双绿，红在哪里就砍哪里。行数不是度量，三重封闭才是。

### 铁律 2：分形——每个插片也是薄主干

薄主干结构**递归成立**：每一个插片，本身也是一层薄主干，带着自己的小插片。

- 插片 ≠ 原子。打开任何一个插片，判据不变：它有没有自己的
  **状态内核 + 可热拔插的子插片边界**？
- 分形没有终止层级，只有"当前实现选择停在哪一层"。
  停在哪层是工程决策（复杂度/收益权衡），不是架构许可——
  停的那一层必须显式声明其子插片接缝（哪怕暂时只有一个实现）。

> 实证样例（lingclaude）：
> `bash` 工具插片内部 = wrap 组装薄内核 + `SandboxProvider` Protocol
> （BwrapProvider / NoopProvider 子插片）；`StateStore` 插片内部 =
> 2T3A 原语内核 + JsonFile / LingYi 后端子插片。

### 铁律 3：变化的全部走接缝，主干零 diff

- 新能力/新后端/新 Agent 落地时，**必须以插片入册**（SeamType 注册 /
  WiringSpec 装配 / PluginLoader 加载），主干代码零修改。
- 临时硬编码一个"以后再抽"的直接调用，即违反本铁律——"以后"不会来。
- **但书（2026-09-17 用户裁决）**：唯一例外是经修剪语法（铁律 4）入册的
  debt record——临时直连允许存续，但必须在台账记账并承诺清除期限；
  无账的临时直连仍然违规。"以后"不会来，但"有账期的债务"是合法生命周期事件。

### 铁律 4：修剪语法——架构必须能自我减肥（2026-09-17 用户裁决升格）

原"修剪语法"条款升格为铁律。铁律 1-3 只给了生长语法（插片入册），
没有修剪语法则接缝棘轮式只增不减，最终接缝体系复杂到没人敢动：

1. **接缝回收生命周期**：单实现且龄期超 N 个月、无扩展意图的接缝进入
   回收候选清单（由 M6 仪表驱动），经审计流程降级回收为直接调用。
   **回收接缝不算主干 diff 违规**，属接缝本身的合法生命周期事件。
2. **违规定价（debt record）**：临时直连允许存在，但必须在 StateStore
   记一条 debt record（位置、原因、清除条件、到期时间）——账是明账，
   且此机制本身符合 J4。debt 到期未清 = 守卫红（守卫即查询的执行点）。
   同模块在册 debt 超额则冻结新功能、先还债。
3. **审计防博弈原则**：静态守卫（M1-M3）只触发人工审查、永不自动通过；
   语义终审只在 M4/M5。度量是尺子不是 KPI——任何架构改进的仲裁问题：
   "这让系统的自描述程度变高了吗？"

### 铁律 5：双向插片互认——我可为人之插片，人可为我之插片（2026-09-17 用户裁决升格，原候选 5）

灵元主干本身满足插片协议（record 值域 + 三算子 + 可拔插接缝，
**插片协议即主干协议**，不分内外）。故灵元主干可**对称地**作为外部系统的
一个插片挂载——"换个 registry 就是另一个系统"（M4）是**双向命题**。

1. **对偶记账状态机**：互账的对偶关系是一条 record（type=`federation_pair`），
   state 走六态：`proposing → paired → drift | broken → restored | dissolved`
   （谁先建/对账失败/删库恢复各有确定语义，drift 由 N5 行为指纹侦测）。
2. **对偶约束（互质权）**：我接受你的审计判据（J1-J5 查到我的账）时，
   也获得我用 J1-J5 查你的账的权利——自由与约束成对，无单向便宜。
3. **对偶故障域**：互挂双方都只是对方的插片不是内核，爆炸半径结构性限死；
   任一方缺席走各自声明的 L2/L3 语义。
4. **升格执行细则**（随 lingxi 试验田 Phase 1 首次实证）：互账 record 双方各持
   一份（先挂载方建"我即你插片"，后挂载方建"你即我插片"）；
   对账由 N1 守卫周期执行；`dissolved` 不允许留半边（单向撤回即整对失效）。

### 铁律 6：信任等级——缝后是黑盒时，审计退化为契约审计（2026-09-17 用户裁决升格，原候选 6）

缝后实体按修复权与可观测性分三级，**SeamType/插片入册时必声明**
（缺省 T1 最严，N2 守卫拒收无声明入册）：

| 等级 | 定义 | 审计方式 |
|------|------|---------|
| **T1 全审计** | 代码在手（仓内插片/协议同源基础设施） | J1-J5 全套 + M 件套 |
| **T2 契约审计** | 黑盒但可观测履约（响应/超时/状态） | 审接口契约非内部 |
| **T3 只观测** | 黑盒且不可强制履约（外部应用/硬件） | 只记健康探针事件，不判违规，只告警 |

**T3 契约漂移条款**：T3 插片若自身具备自优化能力，其接口契约会单方漂移——
每次可观测行为变化记 `contract_drift` record（与 arch_contract_breach 分离：
drift 是契约本身在动，breach 是违约）；drift 入账后引用旧契约的守卫结论
标记 `stale` 直至重验（证据：arch_reference/ref-deepseek-operator +
ref-zg-token-saving）。

### 铁律 7：缝命名空间——分形递归到跨物理边界时，SeamType 须带域（2026-09-17 用户裁决升格，原候选 7）

跨物理层后同名缝在不同层次是**不同实体**（`inf/llama` ≠ `hw/gpu0/llama`），
注册表静默合流即撞名事故。规则：

1. 缝 key 升级为域前缀字面量 `{ns}/{seam}`；域 ∈ `{core, agent, cap, os, hw, gov}`
   （前五域对应四层宏图；`gov` 为治理域——守卫/仪表类插片的注册与执行实现归属，
   **2026-09-24 用户裁决扩域**〔5+1 发展规划 v0.4 议题 B，与规划基线议题 A 同裁〕。
   gov 域物理落地规范：框架住 `core/governance.py` 单轨不改，实现住 `gov/guard/`，
   注册一律收口本注册表；守卫（可拒收动作）与仪表（只观测）须分层级标注，
   守卫目录内不得存放纯仪表实体）；
2. **升降格通道**：竖排不再强制（`core` 域现有 10 类 SeamType 保持原字面量，
   存量豁免），**新增插片必须带域前缀**（N3 守卫拒收裸 key）；
3. 跨域互认时双方声明的域必须一致，不一致即 J5 四条件之 2 的**分歧即警**；
4. 灵元 2T3A + SeamType 定位为**中立的插片互认协议**——不绑定任何主干，
   给 Harness 们发统一的插片证（行业命名战争期的公共缺口，证据 arch_reference/
   ref-codex-harness / ref-hermes-webui / ref-omarchy，快照带 as_of）。

### 铁律 8：可隔离故障域 + 操作域 + 时效域（2026-09-18 用户裁决升格，原候选 8 扩写）

原候选 8 只覆盖硬件层"可感知缺席 + 故障圈死"。work_claim（多 Agent 并行修改
锁）实证出三块同等重要的领地，一次升格，三域齐备：

1. **隔离故障域（原候选 8 本体）**：
   - **可感知缺席**：插片（含硬件）健康探针连续失效 → record transition 到
     `absent`，query 返回 absent 而非假活；
   - **故障圈死**：依赖缺席插片的功能圈死在同一故障域（域前缀即故障域），
     故障不扩散到域外——"拔不掉，但知道它没了，且把依赖它的一圈一起隔离"；
   - N4 守卫：absent 后同域 query 全返回 absent、域外不受影响。
2. **操作域（work_claim 实证新增）——锁互斥 + 独占权可 query**：
   - 并行修改同一代码域的 N 个成员，**任一时刻至多一个持锁人**；
   - 独占权不是口头约定，是 StateStore 里的 `work_claim` record（路径+成员+时限），
     任何第三方（含守卫）可 query"此刻谁锁着什么、何时到期"；
   - **查锁跳过是一等语义**：守卫跑测试前查锁，被有效锁覆盖的模块记
     `skipped:claim-held`（显式留痕），**不静默吞掉**（J5 防博弈：跳过必须可见），
     也不拿别人的半成品当自己的验证基线（lingxi 插片 5-failed 基线漂移教训）。
3. **时效域（work_claim 实证新增）——超时自动失效，不存在永久死锁**：
   - 锁的独占权**有时效**（TTL）：持锁者失联（未 renew 且过期）→ 锁自动
     `expired`，任何人可夺锁/清理——失联的持锁人不能永久冻结全族；
   - 夺锁与清理同样入账（`work_claim_log`：bind_denied/renew_denied_expired/
     released 全事件可回放）；
   - 边界条款：**时效是"失联兜底"不是"常态机制"**——持锁人健在时 TTL 内独占
     不可被夺（互斥优先），只有过期才开夺锁口。

**执行载体**：`lingclaude/plugins/agents/work_claim.py`（bind/renew/release/
holder/check_paths 五原语）+ `scripts/worktree_node.py`（代码层 worktree 隔离
与锁同生命周期）+ `tests/agents/conftest.py`（查锁跳过）+ 测试 16 项（锁 8 +
节点 8）全绿。N4 守卫同步扩为三查：**缺席查（absent 一致性）/ 互斥查（同路径
双活锁即警）/ 时效查（过期锁存在即提醒夺锁）**。

## 二、审计判据（按此执行，替代历史行数判据）

审计任何模块/重构/PR，按以下判据逐条核验；行数仅作背景参考，不作结论依据。

| # | 判据 | 通过标准 |
|---|------|---------|
| J1 | 变化走接缝 | 新功能是否经 type 注册/协议挂载进入，主干（状态机 + 装配器）零 diff |
| J2 | 可拔插可证 | 该插片 unregister/替换实现后，主干与其余插片不感知、不崩溃 |
| J3 | 分形成立 | 插片内部是否声明了自己的内核边界与子插片接缝（Protocol/Backend），而非焊死单一实现 |
| J4 | 状态归原语 | 模块的状态读写是否走 StateStore（records/events/transition），而非私连存储介质 |
| J5 | 守卫同源 | 架构守卫（测试/CI）是否校验 J1–J4，而非按行数/文件数设红线；**测量口径须满足四条件**（见下） |

**J5 测量口径四条件（2026-09-17 用户确认扩充）**：自审依赖测量，测量又依赖自审——
该回归以收敛替代确定性，四条件即收敛机制。任何测量口径（守卫/仪表/工具）不满足即待改造：

**J5 联邦守卫 N1–N3（2026-09-17 随铁律 5/6/7 升格同步入册，配套守卫）**：

| # | 守卫 | 层级 | 度量内容 |
|---|------|------|---------|
| N1 | 互账完备（配铁律 5） | 法 | 双向互认的两侧 StateStore 各有一条对偶 record（federation_pair 同 key 同 state，query 对账缺一/不一致即警） |
| N2 | 信任声明（配铁律 6） | 律 | 插片入册必带 trust_level（T1/T2/T3）+ plug_level（L1/L2/L3），缺省按 T1+L3 最严组合校验；缺字段拒收 |
| N3 | 命名空间互证（配铁律 7） | 律 | 新增插片缝 key 必带域前缀 `{ns}/{seam}`（ns ∈ core/agent/cap/os/hw），裸 key 拒收；跨域互认域不一致即警（core 域存量 10 类 SeamType 豁免） |
| N4 | 三查（配铁律 8） | 法 | 缺席查：插片（含硬件）探针连续失效 → absent，同域 query 全返 absent 不假活；互斥查：同路径/同 tab 双活锁即警；时效查：过期锁/过期探针即提醒夺锁（执行载体 work_claim 三原语 + conftest 查锁跳过） |
| N7 | 横向耦合禁令（2026-09-18 升格） | 律 | plugins/ 下插片禁止 import 他插片内部符号（插片目录=含 plugin.py 的事实边界；含函数内 lazy import），共享只走显式公共接缝（plugins/\<域\>/ 直置共享模块，如 agents/mcp_common.py）；AST 静态口径对齐 M3 家法，豁免走 arch_exemption guard=N7 只缩不放。与 M3 合围依赖图三向封闭：主干↔插片走 M3，插片↔插片走 N7，插片状态↔StateStore 走 J4 |

1. **失败模式显式声明**：口径必须自曝"测的是什么、测不到什么"（如 M6 声明"静态口径看不见动态注册"）——不声明失败模式的测量才是危险的测量；失败模式声明是测量自身的可查询边界。
2. **多口径互证，分歧即警**：单一口径自审是自己证明自己；独立口径（静态/运行时/行为）结论不一致即报警——分歧不是噪声，是"测量里有假"的系统信号。守卫禁止以单一口径出具终审结论。
3. **行为锚终审**：M4/M5 级行为测试（换域/截肢）难以被错误口径伪造，是测量回归的收敛点——静态口径可集体失明，行为事实不会。口径之争最终裁决归行为测试，不归另一层审查。
4. **误差事件入账**：口径失准必须定价留存（arch_review 卷宗 / arch_audit_task / 修订史）——测量不因一次错误报废，也不因一次正确免检；口径可信度在历史中累积，引用测量数字时其误报史可 query。

**J5 守卫件套 M1–M6（2026-09-17 用户确认补充，替代 G10 类行数红线）**：

守卫分两级：**律**（M1–M3 静态检查，便宜即时，只触发人工审查、不自动通过）与
**法**（M4–M5 行为测试，语义终审，无法靠措辞绕过）；M6 为仪表，管趋势不判对错。

| # | 守卫 | 层级 | 度量内容 |
|---|------|------|---------|
| M1 | 概念清白度（词汇封闭测试） | 律 | AST 扫描 core/ 标识符与字符串字面量，对照领域词汇表（含中文词），命中必须为 0；词汇表入册 StateStore，变更须用户确认 |
| M2 | 特判禁令 | 律 | core/ 及装配器中禁止对任何 SeamType/插件枚举值的具体分支判断（AST 检查 if/elif/match 比较对象） |
| M3 | 依赖方向契约 | 律 | core/ import 传递闭包检查，禁止指向 plugins//engine/，覆盖间接路径与 importlib/__import__ 动态调用点 |
| M4 | 换域测试 | 法 | 用合成 registry（人造业务域）装配主干并跑主干测试套件，必须全绿——"换个 registry 就是另一个系统"的可测化 |
| M5 | 截肢测试（amputation） | 法 | CI 中逐级 unregister 插片（1→全部）：主干必须能启动；不依赖被拔插片的用例必须通过；各 SeamType 声明的拔插等级必须兑现。等级未声明默认按 L3（最严）检验 |
| M6 | 接缝生态趋势仪表 | 仪表 | 各 SeamType 实现数分布（**须双口径：静态扫描 + 运行时 get_all 实测，四条件之 2**；单口径结论只可作线索不可作裁定）、单实现接缝龄期、装配 spec 总数周环比——不设红线，保证"没人看"不发生 |

**拔插等级声明义务**（M5 前置）：每类 SeamType 入册时必须显式声明承诺的拔插等级，
禁止用模糊的"可拔插"表述：
- **L1 替换**：A 拔下 B 插上，接口一致即不崩（J2 现行测的等级）；
- **L2 缺席降级**：拔掉后走降级路径——降级实现本身必须是插片（如 NoopProvider 范式），禁止主干内 if-else 降级；
- **L3 缺席裸奔**：拔掉后功能消失但系统不崩，主干零依赖具体功能。

**历史误判修正记录**（防复蹈）：

## 六、联邦层铁律候选（草案，2026-09-17 灵克起草，**未生效——待用户裁决**）

> 状态声明：本节是**候选**，不是铁律。铁律本体（一、二、三、四章）不因本节存在而改变；
> 本节生效须用户逐条裁决升格。背景：用户四层宏图（Agent/能力域/OS硬件逐层插件化）
> + "可把别人变我的插片，也可把我变别人的插片"（双向性裁定）。四层宏图在仓内铁律
> 1-4 的管辖区外——外部黑盒插片、跨物理层命名、联邦互账，是铁律当前未覆盖的三块空白。

### 候选铁律 5：双向插片互认——我可为人之插片，人可为我之插片

- **本体**：灵元主干本身满足插片协议（record 值域 + 三算子 + 可拔插接缝，
  插片协议即主干协议，不分内外）。故灵元主干可**对称地**作为外部系统的一个插片
  挂载——"换个 registry 就是另一个系统"（M4）是**双向命题**：我站上我的 registry，
  你是插片；你站上你的 registry，我是插片。同一套 2T3A，两个方向，零改动。
- **对偶记账（状态机化，2026-09-17d 返审修复：原"双方各一条 record"未定义对偶关系
  本身的状态机，与铁律 1"主干是状态机"语法不一致，已补）**：
  互账的对偶关系本身是一条 record（type=`federation_pair`），其 state 走
  **六态状态机**，谁先建、对账失败、删库恢复各有确定语义：

  | state | 语义 | 进入 transition |
  |-------|------|----------------|
  | `proposing` | A 单方已建"我即你插片"，B 侧尚未建对偶 | A 发起互认 |
  | `paired` | 两侧对偶 record 齐备，对账通过 | B 建对偶 + 对账绿 |
  | `drift` | 两侧契约指纹不一致（N5 侦测） | 行为指纹 hash 分歧 |
  | `broken` | 对侧删库/失联=我死边界（存在证明失效） | 对侧 record 不可 query |
  | `restored` | 冗余恢复后重新对账 | 冗余副本补齐 + 对账绿 |
  | `dissolved` | 互认解除（单向撤回即整对失效，不允许留半边） | 任一方发起 |

  **裁决问题（升格前须定，原 ①②③ 不变，补 ④）**：
  ①互账 record 由哪一方先建（先挂载方建"我即你插片"，后挂载方建"你即我插片"，
  双方对账）；②对侧删库=我死（存在证明依赖对侧存储不丢），互账是否强制各持一份
  冗余；③"联邦"是否允许非灵元主干参与（只认插片协议不认 2T3A 全体的"半认"等级，
  还是必须全 2T3A 互认）；**④`federation_pair` 的对账由谁周期执行——A 侧 SDT、
  B 侧 SDT、还是中立对账服务（N1 互账守卫的运行时形态）；drift 态的仲裁顺序是否
  沿用 J5 效率层"②③ 联合否决 ①"**。

### 候选铁律 6：信任等级——缝后是黑盒时，审计退化为契约审计

- **本体**：仓内插片代码在我手里，审出问题→入 arch_audit_task→等待修复（全审计）。
  仓外插片（Claude Code/某 OS/某硬件）我没有修复权，只能审它**履约**
  （响应协议、状态可信度、降级行为）——契约审计。
- **三级信任**（SeamType 入册时必声明，J2 拔插等级的第四块拼图）：
  - **T1 全审计**：代码在我手（仓内插片），J1-J5 全套 + M 件套守卫覆盖；
  - **T2 契约审计**：黑盒但我可观测其履约（响应/超时/状态），审的是**接口契约**非内部；
  - **T3 只观测**：黑盒且不可强制履约（物理硬件/第三方服务），只记**健康探针事件**，
    不判违规（判了也没执行权），只告警。
- **裁决问题**：T2/T3 插片的"违规"入 arch_audit_task 还是入新 type
  `arch_contract_breach`（契约违约台账，与架构债务分离）；T3 插片的探针频率
  是否归 M6 仪表管（趋势）还是归 SDT 巡检管（实时）。
- **T3 契约漂移条款（2026-09-17 参考资料增补，证据入台账 `arch_reference`：
  `ref-deepseek-operator` + `ref-zg-token-saving`，快照带 drift_note 可 query）**：
  T3 级插片若自身具备自优化能力（像 AI 独立重写算子 kernel），其**接口契约会随
  时间漂移**——你审计的契约对象在单方面升级，基于旧契约的全部审计结论自动过期
  （灵元栈"TPS 假值审计"踩坑同款：旧代码测的数字不能背书新代码）。
  故 T3 插片每次可观测行为变化须记一条 `contract_drift` record（type 与
  arch_contract_breach 分离：drift 是契约本身在动，breach 是违约）；
  drift 入账后，引用旧契约的守卫结论标记 `stale` 直至重验。
  **裁决问题追加**：contract_drift 的探测靠探针差分（行为指纹 hash 变化即 drift）
  还是靠插片方自报（版本字段），两者可信度不对称。

### 候选铁律 7：缝命名空间——分形递归到跨物理边界时，SeamType 须带域

- **本体**：仓内 SeamType 是全局字面量（`TOOL`/`PROVIDER`）。跨物理层后同名缝
  在不同层次是不同实体：`inf/llama`（我的推理栈插片）≠ `hw/gpu0/llama`
  （某台 GPU 上的模型服务插片）。注册表若静默合流，跨层互认即撞名事故。
- **规则**：SeamType 入册 key 升级为**域前缀字面量** `{ns}/{seam}`；域 ∈
  `{core, agent, cap, os, hw}`（对应四层宏图）；跨域互认时双方声明的域
  必须一致，不一致即 J5 四条件之 2（多口径互证）的**分歧即警**。
- **裁决问题**：域前缀是改 `SeamType` 枚举本身（影响现有 10 类 SeamType 全部
  入册点），还是另开 `SeamNamespace` 平行维度（SeamType 不动，加 ns 字段）——
  前者彻底但迁移大，后者渐进但留两期双轨。
- **行业命名战争实证（2026-09-17 参考资料增补，证据入台账 `arch_reference`：
  `ref-codex-harness` / `ref-hermes-webui` / `ref-free-claude-code` / `ref-omarchy`，
  快照值带 drift_note——star 数/插件数会漂移，引用时须注明 as_of，引用 stale 值
  须先重验，N5 同款纪律）**：
  当前行业正处在"缝的命名空间战争期"——各家 Harness/平台无统一标准，各自长出
  自己的插片协议：OpenAI Codex App Server（JSON-RPC 接任意应用，ARC-AGI3 13.3%→
  38.3% 快照值见台账）、DeepSeek Harness（"一切皆插件"）、Hermes WebUI（集成
  CodeX/DeepSeek/Claude/Grok/OpenCode 的群聊面板）、free-claude-code（9 Agent +
  50 provider 统一面板）、Omarchy（DHH，AI 原生 Linux，十天千级插件快照值）、
  teamai-cli（Skills/Rules/MCP/知识库进共享 Git 仓）。它们互认插片时即撞名：
  你家的 `agent/claude` 和我家的 `agent/claude` 是两个实体还是同一个？域前缀
  互认协议（N3 守卫）不是灵元私有需求，是这批"杂乱"的公共缺口——**灵元 2T3A +
  SeamType 有机会做中立的插片互认协议（不绑定任何主干，谁都能把谁当插片），
  不是再造一个 Harness，是给 Harness 们发统一的插片证**。裁决问题追加：中立
  互认协议是纯文档（registry schema + 命名约定）还是须有运行时（跨仓
  SeamRegistry 对账服务，N1 互账守卫的联邦版）。

### 候选铁律 8：可隔离故障域——硬件层不承诺可拔插，承诺可感知缺席 + 故障圈死

- **本体**：代码插片拔了主干照跑（L1/L3 已证）。硬件插片（GPU 宕机/OS 蓝屏）
  缺席是物理事实，**L2 降级、L3 缺席裸奔常兑现不了**——灵元"拔除后主干继续运转"
  的承诺到物理层须改口为：
  - **可感知缺席**：硬件插片的健康探针失效即 transition 到 `absent`（record 状态），
    主干对该插片的 query 返回 absent 而非假活；
  - **故障圈死**：依赖该硬件的功能圈死在同一故障域（SeamType 族 + 域前缀即故障域），
    故障不扩散到同族之外的插片——"拔掉不了，但能知道它没了，且能把依赖它的一圈功能
    一起隔离，不拖垮全主干"。
- **裁决问题**：故障域粒度（SeamType 族级 or 单插片级 or 域前缀级）；
  absent 态插片是否占用注册表槽位（占：故障域可枚举；不占：缺席即消失，圈死靠事件）。

### 候选 J5 守卫扩展（配套 M 件套，与上述四候选铁律对应）

| 候选守卫 | 层级 | 度量 |
|---------|------|------|
| N1 互账完备 | 法 | 双向互认的两侧 StateStore 各有一条对偶 record（query 对账，缺一即警） |
| N2 信任声明 | 律 | SeamType 入册必带信任等级（T1/T2/T3），缺省 T1（最严），T2/T3 须注明黑盒边界 |
| N3 命名空间互证 | 律 | 跨域互认时域前缀一致（J5 四条件之 2 的跨系统版），不一致即警 |
| N4 故障域圈死（2026-09-18 随铁律 8 三域升格扩为三查） | 法 | **缺席查**：插片 transition→absent 后，同故障域内插片 query 全返回 absent，域外不受影响；**互斥查**：同路径双活 work_claim 即警（操作域锁互斥，铁律 8 第 2 条）；**时效查**：过期 work_claim 存在即提醒夺锁（时效域，铁律 8 第 3 条）；被锁模块的测试跳过须显式记 `skipped:claim-held`，静默吞掉即警 |
| **N5 契约漂移侦测（参考资料增补，配 T3 契约漂移条款）** | 律 | T3 自优化插片的行为指纹 hash（关键路径输入→输出摘要）变化即记 contract_drift；引用 stale 结论的守卫测试标记待重验，不得沿用旧数字背书新行为（证据 `arch_reference/ref-zg-token-saving`：zg 实测 token 省 37.6% 为**单口径快照值**——测量口径直接决定成本，旧口径省的数字可能正是误导口径省出来的，引用须附 as_of） |
| **N6 口径成本互证（参考资料增补，配 J5 四条件效率层）** | 仪表 | 同一任务在多个测量口径下的成本差（token/延迟/工具调用数）并入 M6 趋势仪表，**只产出线索（单口径结论标记 `unverified`）不直接红**；"单口径结论须附第二口径对照，否则只作线索不作裁定"是**使用方纪律**（引用者遵守），不是仪表的强制动作——仪表自身判"须/不得"违反 M 件套层级语义（仪表不判对错，2026-09-17d 返审修复：原条文把使用方纪律写进了仪表层，已归位） |
| **N7 修剪执行移交（参考资料增补，配 RSI 缺口）** | 仪表 | 输出"执行层移交进度仪表"（移交次数/结果分布/驳回率），**只观测不裁决**；"规则层人裁决、执行层逐步移交模型自审"是**组织决策**（人随时可否决），不是仪表动作；移交的每次结果入账 arch_audit_task 是铁律 4 既有语法，非 N7 新增强制 |
| **N8 free-RAM 环境守卫（2026-09-24 主裁 B1 裁决 gov/ 域注册）** | 守卫 | 可用内存（/proc MemAvailable）< 阈值（默认 1024MB，env `LINGCLAUDE_FREE_RAM_GUARD_MIN_MB`）即拒收启动类动作（新会话/优化周期），防 2026-08-21 21GB thrash 复蹈；采样失败 fail-open 放行留痕（守卫失效绝不静默）；实现 `lingclaude/gov/guard/free_ram_gate.py`，接线 `cli/app.py`（run/daemon run）+ `self_optimizer/daemon.py run_once` |
| **N9 RSS 增长看门狗（2026-09-24 撞号修复注册；ops 实现原误标 N6）** | 仪表 | 长会话 /proc RSS 采样（`lingclaude/ops/rss_watchdog.py`，挂点 `_record_long_task_metrics`）：增长 ≥500MB WARNING、绝对值 ≥ 有效硬限（max(1000MB, 基线+增长线)）ERROR + LingBus 告警，基线重置防稳态泄漏轰炸；**只观测不拒收**——拒收语义归 N8 守卫，二者分层互补 |

> **层级语义修复注（2026-09-17d 返审失锁①）**：M 件套层级定义中"仪表=管趋势不判
> 对错、不设红线"。N5-N7 初稿把"须附/不得/即记"写进仪表条文，层级列与条文语义脱节——
> 修复后：**律层（N5）保留强制动词**（contract_drift 入账是守卫动作，红即触发人工审查，
> 符合 M1-M3 律的语义）；**仪表层（N6/N7）只描述观测产出**（unverified 标记/进度分布），
> 强制语义（"单口径结论只作线索""执行层可移交"）上移到使用方纪律与组织决策两条
> 独立表述，不与仪表动作混写。

### J5 四条件效率层增补（2026-09-17 参考资料，配 N5/N6）

J5 测量口径四条件原为**审计层**判据（守卫查得准不准）。参考资料照出它还需下沉到
**效率层**：测量口径不只是"审得对不对"，更是"系统跑得快不快、省不省"——
- 口径 ①（静态 AST）查架构合规，口径 ②（运行时/行为指纹）查实际履约，
  口径 ③（成本度量：token/延迟/工具调用）查效率；三口径任一单独出具结论都可能是
  误导口径（M6 TOOL 误报是 ①② 打架的实例，zg 数字是 ③ 的单口径陷阱）。
- 新增裁决问题：三口径不一致时的仲裁顺序——建议 **②③ 联合否决 ①**（行为与成本
  事实优先于静态结构推断），但 ① 的"结构性违规"（如 M2 特判）仍单独成立，
  不因 ②③ 绿而豁免。
