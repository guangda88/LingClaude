### Blocker

### High

**H-1｜seam_backend.py importlib 兜底路径：合规但有守卫绕过风险**
- 证据：`engine/subagent/seam_backend.py:144-171`
- 事实：已知线索属实。`reload_agent_plugins()` 优先取 `sys.modules` 单例（:156），缺席时退 `spec_from_file_location` 按**文件路径**装载（:161-170），绕开包 import 语义。docstring 自述"对齐 PluginLoader 通路语义"（:151-152）。
- 风险：①路径构造 `Path(__file__).parents[2]/"plugins"/"agents"/"registry_loader.py"`（:161-163）**硬编码相对路径**，包结构变动时静默失效；②M3 动态 import 检测基于 AST 扫描 `lingclaude.plugins` 字符串前缀（`test_iron_law_guards.py:391`），此处模块名以字符串传入（:165）——已确认被覆盖，风险收敛；③残余风险：`exec_module` 不注册进 `sys.modules`（:169-170），与注释声称的"幂等单例"（:150）语义有缝——每次缺席都重新 exec，插件内模块级状态会被重建。
- 修复建议：①路径构造失败时 log 明示解析出的绝对路径；②exec 后补 `sys.modules.setdefault(...)` 或注释说明刻意不注册的语义。

## 7. 附记：sub_agent 两次 429 硬配额耗尽复盘

**现象**：本次审计原计划拆给 sub_agent（inprocess provider），两次调用均返回 `429 hard quota exhausted`，降级为主会话直接执行。

**机制核查（代码证据）**：
- `lingclaude/engine/subagent/inprocess.py:76,95` — inprocess backend **复用主会话的 model_provider**（`_resolve_provider(ctx.model_provider)` 解析 SlotHandle 后交给 SubAgent 调 `.complete()`）。**即 sub_agent 走的正是 k3-256k [PINNED] 同一 provider 实例、同一 API key**。
- `lingclaude/model/openai_provider.py:197-227` — 429 处理路径：退避重试 + 熔断计数（`_circuit_consecutive_429`，1308 事故后修复）。
- `lingclaude/model/health_ranking.py:13,24` — 429 在可用率中折算 0.5（节点活着但限流）。

**结论**：不是"没用 k3-256k"——恰恰相反，**正是用了同一个 k3-256k**。429 是上游 API 侧对同一账号/密钥的配额硬限制：主会话 + 2 个并行 sub_agent = 3 路并发流打向同一 key，触发上游硬配额（RPM 或并发上限），inprocess 语义决定了子代理无法绕开主会话的钉住模型。

**启示**：
1. inprocess sub_agent 与主会话**共享配额**——并行拆子代理在配额紧张时反而放大 429 风险；
2. 如需子代理走独立配额，须用 acp provider 或显式指定不同 model_provider（`SubagentRequest.provider` 已可配置，`inprocess.py:4`）；
3. 429 退避重试对"硬配额耗尽"无效（`openai_provider.py:442` 注释：GLM 1308 5h 限额退避无意义，直接失败）——快速失败降级主会话是正确行为。
