## 二、12 条优化方案（按 ROI × 可实施性 重排）

### P0（立即可动，本会话内）

#### R1：denial ≥2 次同类自动停手（用户代理协议）

**问题实证**：5 次 denial 中 3 次集中在 9-06 一天；后半段 9-07/9-08 长出 ~50% 时间**0 新 denial**——**学习曲线存在但人工记忆不可靠**。

**机制**：作为我自己推理层的内化规则（无需新工具）：
```
if same_denial_class_count >= 2 (last 3 attempts):
    STOP retrying.
    Report user with full context: command + reason + suggested next step.
```

**预期**：未来同质 denial 三连击场景砍掉 600-900 token 解释浪费。

#### R2：denial 自动写 `.audit/denials.log`

**机制**：每次 denial 触发时同步追加一行：
```
ts | kind | cmd_prefix | reason | ctx_hash
```
让 handoff 文档能引用历史 denial 模式。

**实施成本**：~20 行（hook 或 my reasoning 层）。

#### R3：H17 文档同步（修正 P2 降级为 P1 的债）

**问题**：方案文档 `docs/cli/TUI_BOTTOM_INPUT_DESIGN.md` 写"常驻可见性由 P2 全屏 TUI 解决"，实际走 P1 降级（bottom_toolbar 仅 prompt 渲染期可见）。**文档与落地不同步** = H17 完整破坏。

**修正**：在设计文档加一段"实际落地 § P1 降级"小节，明示当前形态 vs 设计承诺差距。

**实施成本**：~30 行 doc。

### P1（环境层 + 治理层，需权限/族内协调）

#### R4：`/dev/null` / MCP / pytest 启动自检

**问题**：自评说 `/dev/null` cgroup 拒写导致 git/pytest 全废——**本会话所在环境不复现**（`/dev/null` 666 + ai:1000 工作正常），但**容器化部署时该问题真实存在**。

**机制**：lingclaude 会话启动时跑一次自检（输出到 stderr，仅 warning，不阻塞）：
- `/dev/null` 可写性探测
- `git/pytest smoke test`
- MCP 通道连通（不连 OK、连不上 OK、错连 ERROR）

**实施位置**：`lingclaude/self_optimizer/daemon.py` 的会话健康检查（叠加 R2 已合规的 daemon cycle）。

#### R5：检查点式持久化（kill 不全损）

**问题实证**：57109 误杀——"退出才落盘"的策略让整个会话上下文随进程消失；幸而**用户保存终端回显**才能事后恢复，**这不是工程方案，是偶然好运**。

**机制**：关键动作（文件写、阶段结论、发现）发生时**立即追加 journal**（append-only），不在退出时一次性写。

**实施位置**：`lingclaude/cli/app.py:_interactive_loop` 关键点 hook；fallback 到现有 `session_records/` 路径。

**预期**：被误杀时**最多丢一条消息**，而非整段。

#### R6：监督者判活升级

**问题实证**：57109 被杀的真因 = 监督者仅凭 CPU 采样判死（CPU=0 ≡ "挂机"），实际是 LLM 网络响应等待中。

**机制**：复合判活信号——
1. 会话日志 mtime 最近 N 分钟有更新
2. agent 心跳文件定期 touch（每 30s）
3. **查询中（LLM 调用进行中）一律不算挂机**——这是个静态规则，监督者接入即可

**实施位置**：族级**监督者侧**，不是 lingclaude 内。

### P2（设计层，长期）

#### R7：黑名单参数级解析

**问题实证**：`'apt'` 裸词匹配 `--capture`（已修）；`'at '` 匹配 `cat`、`stat`（部分修）；双层守卫（bash 本地 + lingxi MCP 通道）规则不一致。

**机制**：
- 危险命令走 token 化精确匹配（`shlex.split` 后首词 + 关键参数）
- 双层守卫同源单份配置（消除漂移）
- 拦截理由返回结构化（含命中规则 ID + 建议替代命令），不再裸错误

**实施位置**：`lingclaude/engine/bash.py` + `lingxi` MCP 通道（族级协调）。

#### R8：sub_agent 通道修复

**问题实证**：57109 记录段 6"ACP/inprocess 后端均未通，大规模搜索委派不出去，主会话硬扛"——本会话 1100 万 token 一半是 sub_agent 不可用导致的。

**机制**：
- 给 `engine/subagent/` 引入真 in-process backend（当前是死路径）
- 委派一次只读子代理 = 主会话省几十轮 token

**优先级升 P0**（从自评 P2）：单纯靠会话预算收口只能省 30-40%；子代理打通是**结构性省 token**。

#### R9：long-task 分段 + 恢复协议

**机制**：超长任务强制分段，每段结束输出**结构化 checkpoint**（目标 / 已完成 / 下一步 / 未决问题），新会话可从 checkpoint 无缝续跑。

**对应方案族**：钱学森"增益纪律" + Kelly"组块生长"——复杂系统只能从简单系统增量组装。

**实施位置**：`lingclaude/cli/interface.py` 新增 checkpoint 协议（用户在 `/checkpoint` 触发）；不强制分段（用户有权决定）。

#### R10：denial 工具调用熔断

**机制**：同一命令连续失败 ≥2 次 → 自动降级为"换策略 / 求救 / 记录待办"，不在同坑烧预算。

**实施**：与 R1 联动；R1 是 denial 间熔断，R10 是同命令内熔断。

### P3（治理/UX 层，可选）

#### R11：会话级预算

**机制**：累计 token > 500 万 → 提示"建议收尾"；> 1000 万 → 强制收尾并写 handoff。

**实施位置**：会话外部（不需 lingclaude 改动）；hook 监控 `.audit/` token 累计。

#### R12：跨 agent handover 标准格式

**机制**：任务交接时附带结构化上下文包（任务目标 / 已完成清单 / 关键文件路径 / 已知坑）。

**实施**：沿用 LingBus 消息总线；hander.md 已存在但稀薄，需模板化。

### 7.1 三条系统性问题的修正

#### 问题 1：把"工程问题"和"行为问题"混为一谈

**纠正**：R1/R2/R10 是行为层（靠模型自觉），R5/R6 是工程层（确定性兜底）。**前者收益不稳定，后者才是底线**。

| 行为层（R1/R10/R11）降级理由 |
|---|
| R1 "denial ≥2 次同类自动停手"——**模型在长任务里恰恰最可能忽略自设规则**。应至少在**工具执行层做硬熔断**（同 denial key 连续 2 次→停止该工具调用），推理层规则只是补充 |
| R11 "会话预算 500 万提示 / 1000 万强制收尾"——本会话 cache_read 复用 2017%，长会话的边际 token 成本被 cache 摊薄，**强制收尾 + handoff 反而触发冷启动重建上下文**，可能更贵。**阈值硬编码缺依据**，建议不强制，阈值跟实际 cache 命中率挂钩 |

#### 问题 2：样本量太小却给精确百分比

**纠正**：3 次真 denial 支撑不起 ROI 定量（"600-900 token 节省""< 0.3% 占比"），**所有百分比改用定性表述**。本会话已通过评审者"n=3 不够"的提醒修正——§一指标保留绝对值，移除"减少 X%"类断言。

#### 问题 3：多条之间语义重叠，文档没做合并

**纠正（合并去重后）**：

| 合并前 | 合并后 | 理由 |

### 7.3 文档缺失项的修补（4 项）

#### 缺失 1：checkpoint 的副作用语义（最关键遗漏）

**问题**：长任务常含写文件、跑命令。崩溃恢复后重放工具调用可能**重复写 / 重复执行**（已写一半的文件、已发的消息）。12 条全在讲"怎么恢复上下文"，没人讲"恢复后怎么避免重复副作用"。

**修补（R5/R9 合并方案必须含）**：
- **工具调用幂等 ID**：每个工具调用 entry 带 `idempotency_key`（如 `tool_call_id` 或 `path+mtime` hash），重复执行结果可预测
- **副作用工具（write / bash 非只读）**：恢复前**二次确认**或**自动跳过**——不能盲目 replay
- **写操作双阶段**：先写 tmp + 记录 intent，崩溃恢复时检查 intent 是否完成

#### 缺失 2：history 双写 bug（**实测已修**，9-09 校正）

**位置**：原指 `model_call.py:380` done 前写一次 history + `app.py:902` 又写一次——长会话每轮历史翻倍。

#### 缺失 3：checkpoint 与上下文压缩的交互

**问题**：长会话靠 compact 续命，但压缩后消息被摘要，**checkpoint 里存的是压缩前还是压缩后的 messages？恢复时用哪份？** 不定义会导致 resume 后上下文错乱。

**修补**：checkpoint 存 **`messages` 的引用 + `compact_after_turns` 标记 + 最近 N 轮原始 delta**——恢复时按当前压缩进度拼回。**不要存全量 messages**（每次 compact 都会变）。

#### 缺失 4：持久化写入频率的 I/O 成本

**现状**：`persist_session.save()` 是全量 json.dump（1096 轮如果每轮覆盖写，写放大明显）。

**修补**：append-only journal（每条增量 200-500 字）+ 周期 checkpoint 合并（每 N 轮或每 5 分钟）；journal 写入 O(1)，合并时 O(N) 但频率低。

#### 反向 #1："输出/输入比 6.98% 正常"可能是误判

**评审者观点**：低输出比 + 2017% cache 复用，可能解读为"模型在超长上下文里大量读进但产出很少"——cache 让这显得便宜，**但上下文本身已超出模型有效注意力窗口**。省 token 不如缩短有效上下文。
