# 一页纸案例分享：给 AI 编程助手做"外科手术"——Lingclaude 重构实录

> 作者：（你的名字）｜ 方向：AI 工具应用 ｜ 2026-09

## 1️⃣ 一句话结论

**AI 编程助手不是"更强就行"，而是"更少犯错 + 更快自愈"**——我用一个月把自用的 AI 助手 Lingclaude（对标 Claude Code 的开源 TUI）重构了 5 个核心部位，改完之后它在 8 小时长会话里不再死锁、不再瞎编、不再重复踩同一个坑。

## 2️⃣ 背景痛点（重构前）

| 症状 | 真实事故 |
|---|---|
| TUI 卡死 | 交互提问组件 `request_user_input` 死锁，整个会话冻结 |
| 越聊越笨 | 长会话里 AI 拿缓存旧文件当代码，改错位置 |
| 幻觉路由 | 模型名不在清单里，AI 顺着记忆"编"出一个回答 |
| 重复犯错 | 同一坑栽两次：诊断网络问题靠猜，不做实证 |

## 3️⃣ 三板斧（可复制的做法）

**斧一：死锁根治 = 熔断降级 + 超时兜底** 🔧
交互组件死锁不是"修 bug"能解决的，我改成双保险：交互失败立即熔断降级为纯文本问答，加 120s 超时兜底，死锁现场自动沉淀为经验规则（LearnedRule），下次不再犯。
→ **启示：对"可能卡死的组件"，兜底比修复更重要。**

**斧二：重读税短路 = 缓存命中不回全文** 📉
AI 每次重读文件都要吞一遍全文，实测长会话 35.7% 的 token 浪费在"重复读没变过的文件"。改成缓存命中只回一句"文件未变"，token 立省 1/3。
→ **启示：先量化浪费（35.7%），再动手优化——数据先行。**

**斧三：实证优于推断 = curl 代替猜测** 🔍
排障"模型不通"时 AI 两次用进程名推断得出错误结论。最终一条 `curl` 实测 4ms 返回 200，真相 3 秒水落石出。团队把它固化成纪律：**能实测的绝不推断，判断只基于工具真实输出**。
→ **启示：AI 最大的风险不是不会，而是"自信地猜"。**

## 4️⃣ 成果

✅ 死锁 0 复发（守卫台账登记） ✅ token 省 35.7% ✅ 错误复发率 46%→治理中（1518 个修复沉淀） ✅ 全部有测试钉住（pytest 32/32）

## 5️⃣ 你可以立即行动的三步

1. 给你常用的 AI 助手加一条规则："**涉及网络/进程/配置的判断，必须先跑一条实测命令**"；
2. 统计它的 token 消耗，找出"重复读文件"这一项——大概率也是最大浪费；
3. 任何交互式组件，写代码时就配好超时和降级路径。
