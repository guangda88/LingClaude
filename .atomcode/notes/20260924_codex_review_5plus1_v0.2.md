# Codex 战略层评议：灵族未来发展·5+1 层架构修订规划 v0.2

> 评议人：codex（灵克重派，补上轮超时缺席的战略层视角）
> 日期：2026-09-24
> 依据：`20260924_future_development_5plus1.md`（评议对象 v0.2）、`docs/LINGYUAN_IRON_LAW.md`、`docs/ROADMAP.md` + 灵克仓内实测（git show / grep / ls）

## 判定（结论先行）

**需修订后再裁。**

v0.2 的架构方向（5+1 层、L1→L2 临界路径、gov/ L0、owner 只写灵族）与三处结构性修订
基本成立，不作架构否决。但存在 **1 处编号冲突硬伤**（rss_watchdog 自称 N6，撞铁律已登记的
N6=口径成本互证）、**1 处过时标签**（"铁律 7 候选"，实已升格）、**4 处未被"实测核对"覆盖的
事实偏差**（CI 未纳入、benchmarks 有真实未查数据、路径笔误、22/107 计数差）。这些不推翻
架构，但提交主裁前须先清，否则会把一个可核验事实错误带进基线。

## A. 三处结构性修订是否成立

### A① owner 只写灵族成员、外部 agent 降为咨询输入 —— 成立（有残留冲突）

自洽性正面成立：本规划 §1.6 自己批评算力供应商"SLA 未列明"，对外部 agent 同样适用——
cc/crush/opencode/codex 均无可用性 SLA，作关键路径 owner 不可押。降级为咨询输入逻辑闭环。

残留问题（§1.4 / §1.5 / §9.2 未同步）：
- §1.4 仍写 "owner：CC + opencode 双家打头"；§1.6 保留 "Crush 担任 agent 域「挂载纪律哨兵」"；
  §9.2 汇总表仍是 crush「挂载纪律哨兵」、CC「L4 拆 L4a/L4b」的贡献化表述。§五 owner 矩阵已全改
  "降为咨询输入"，但正文 1.4/1.5 与 9.2 三处未回改，存在同文档前后打架。
- codex 降级理由之一"评议超时未返"，存在"迟到者被除名→理由又引用迟到本身"的循环自强化；
  建议把降级依据只锚到"外部 agent 无 SLA"这一稳定判据，不引用当轮超时。

结论：**修订成立，但需同步 1.4/1.5/9.2 三处残留命名。**

### A② gov/xcut/ 四横切层收敛为文档标签 —— 成立（v0.2 最大进步，但留命名分叉）

四横切（test/observ/biz/env）分别有现成载体（J6、record 字段、J6 用户故事、N8），
不设独立守卫编号/台账，符合铁律"薄主干·避免双轨台账"（LINGYUAN_IRON_LAW.md 铁律 4 债务明细
思维）。方向正确。

但命名分叉风险：§1.0 主张 L0 用 `gov/iron_law_N`、`gov/guard/N1` **专用命名空间**；§二 又主张
gov/xcut/ **不设守卫编号**。而 §四/§1.5 又要 rss_watchdog 挂 `gov/guard/N6`。三套命名
（gov/xcut/ 标签 / gov/guard/N* 守卫 / gov/iron_law_N 宪章）在同一 L0 域内并存，有再次分叉
成"守卫目录 vs 横切标签目录"的隐患。建议 v0.2 明确：gov/xcut/ 只作归档标签、gov/guard/ 只挂
已入铁律注册表的守卫，两者不设交叉。

结论：**收敛方向成立，命名边界须再钉死一行。**

### A③ 三个月"11 轨"并行 与 冻结条款自洽性 —— 不成立（缺裁剪结论）

§四 3 个月里程碑表实测 **12 行**（L0×3、L1、L2、L3×2、L4a、L4、L5×2、ROADMAP 回写），
即 12 条并行轨；而"冻结条款"（§七 风险表 line 281）只冻结 L1 装配外移期间的**自优化线一条**，
对其余 11 条轨无任何收敛约束。11/12 轨并行与单点冻结之间没有"按 critical path 收敛"的裁剪结论。

评审意见：critical path 图（§三）已把 L1→L2 标为全链主干，但里程碑表未据此排序——L4a 端到端、
L5 GPU v4、ROADMAP 回写与 L1 M1 排在同一 P0 三月窗口，实质是"全都要"。建议增一句裁剪判据：
三月内只保 L0 三轨 + L1 M1 + L2 熔断 + L3 单 OS 隔离 6 条硬轨，其余（L4a/L4/L5×2/ROADMAP）
降 best-effort 或顺延 6 月。

结论：**③不成立，是 v0.2 仍缺的核心战略裁剪纸。**

## C. 5+1 层架构本身的战略风险

### C1 L1→L2 临界路径：方向正确，前置"自优化线收口"缺 done 判据

coding.py 装配外移 + agent-gateway 熔断作全链主干，是 4 家共识且与 mountable proposal M1
一致，方向无疑。但前置条件"等自优化线收口"是**软前置**：无验收判据，"收口"可被无限期引用
而 L1 永不启动。建议给 M1 一个可测启动门槛（如"自优化线 N 个遗留 debt 清零 + 全量回归绿"），
否则 7637cc3 装配时序坑的规避会异化为永久搁置。

### C2 L3 跨 OS"单 OS 租户隔离"降级：合理，"最小验证"边界过窄

先交付单 OS 多进程租户隔离（bwrap + 多租户会话隔离）、跨 OS 设备发现后置 6 月，符合铁律 8
已给的单机"故障域/操作域/时效域"分层。但"1 台异 OS 设备最小验证（1 条指令+1 次回执）"的
验收边界未定义回执的语义载体——回执是不是 record？落在哪个 StateStore？不定义则"实跑 PASS"
无从核对。且 LINGSHELL 单 OS 现状声明（§6.4）正确，避免 ROADMAP 误读。

### C3 L5 HAL 白皮书优先级：略高估，真卡点是故障域仲裁自动化

§1.6 把"HAL 接缝白皮书"列为"硬缺口必须三个月内解决"。但 HAL 白皮书是"标准接口文档"级产物，
不卡任何代码路径——真正卡点在"故障域仲裁自动化（8/7 OOM 活锁靠人工恢复，0 自动化）"与
token schema 收尾。6 月里程碑表其实已有"HAL 白皮书 v1"，三月硬约束应聚焦故障域仲裁自动化，
HAL 白皮书可顺延。当前把文档级产物排在与代码级硬缺口同级，优先级失真。

## D. v0.2 仍缺的战略盲点（§九.3 自报之外，实测补充）

1. **N6 编号冲突**（见 B②）：v0.2 把 rss_watchdog 当"N6守卫"时未对照铁律注册表。
   这是本节最具体的硬伤，提交主裁前必改。
2. **CI/CD 已存在但被当"假设"**：`.github/workflows/` 实测有 `ci.yml`、`ci.yml.bak`、
   `codeql.yml` 三个文件。§九.3 却写成"如有 k8s/terraform/argo 是一整层"的假设语气。
   横切 gov/xcut/test 的 owner 是灵安"CI 红线"，CI 未纳入 5+1 映射是整块遗漏。
3. **benchmarks 有真实高相关未查数据**：`benchmarks/` + `.benchmarks/` + `.repobench/`
   实测含 `laya_cpu_bench_results.json`、`laya_cpu_bench_v3.py`、`humaneval` 等，
   直接关系 L5 GPU 评估 v4 与算力账单重构。§九.3 "benchmarks/ 未查"属实，且该盲区非空。
4. **"铁律 7 候选"是过时标签**：§一行总览（line 12）与 §1.0 仍称"铁律 7 候选"，但
   `LINGYUAN_IRON_LAW.md:111` 已标注"铁律 7 … 2026-09-17 用户裁决升格，原候选 7"。
   铁律 7 已是升格铁律（非候选），且其域集是**封闭五域** `{core, agent, cap, os, hw}`。
   v0.2 新增第六域 `gov/` 本质是**对已升格铁律 7 封闭域集的扩展**，需主裁升格裁决，
   不能只当"文档回写"处理（§6.1 未点破这一裁决性质，只写成"加 gov/ 域前缀段落"）。
5. **跨仓接缝仍未闭环**：token 收尾里程碑提到"灵忆镜像消费"，这是 lingmemory↔lingclaude
   跨仓接缝，但消费方清单未含 lingmemory 仓的消费口径，与 §九.3 自报"跨仓未读"叠加，
   仍是真实糊点。
6. **L4a cap 域 50 工具上限与铁律 4 修剪语法的衔接未写**：§1.5 定"单域上限 50 工具防膨胀"，
   但未说明超限后走铁律 4 回收（`LINGYUAN_IRON_LAW.md` 铁律 4 接缝回收生命周期）还是走
   插片延后装载（12a1251 模式），两条规则可能打架。
