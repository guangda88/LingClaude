# 守卫方法论：机制型 / 认知型双性分类法

> lc 17 守卫（H1-H17）落地一年后的核心教训：守卫分两性，封装方式必须分流。

## 双性分类法

| 性质 | 判定标准 | 正确形态 | 反例（假守卫） |
|---|---|---|---|
| **机制型** | 确定性逻辑可判定（计数/比对/清单核验/阈值） | 代码守卫（`gov/guard/` 插片）或 MCP 工具 | 该代码化却停留在文档，靠自觉执行 |
| **认知型** | 需模型自律（自问、反思、根因挖掘） | 纪律文档 / skill / prompt 注入 | 代码无法验证模型真自问了，却假装拦截 |

## lc 17 守卫速查（按双性归类）

- **机制型（可代码化）**：H1 唤醒序列（checklist 可编排）、H2 循环检测（历史比对 ≥3 同结果熔断）、H7/H16 邻居与模型健康（探活）、H15 工具降级（连续失败计数器）、H17 闭环申报（verify_log 证据核验）、SDT 收敛反查（清单核验）。
- **认知型（保持纪律）**：H13 输出前自问 sure?、H14 双因追问（挖到根因才报告）、H5 退化检测、H12 前提推翻回退。
- **混合型**：H4 范围蔓延（计数可测、意图需判断）——机制部分代码化，判断部分纪律化。

## 机制型守卫接口范式（lc 先例：free_ram_gate）

```
check_xxx(...) -> (passed, reason)          # 单一入口
失败语义: fail-open + WARNING 显式留痕       # 守卫失效宁可放行, 绝不静默
阈值/开关: env 可配置, 豁免必须留痕          # LINGCLAUDE_*_GUARD_* 命名
裁决结构: 对齐统一 gate 结构（passed/checks/warnings/error）
留痕查询: recent_rejections(limit) 供 doctor/audit 消费
```

## 认知型守卫纪律范式

- 一次性指令无效——纪律必须挂在固定动作上（输出前、报告前、完成申报前）。
- 用「检查清单工具」替代「祈祷式提醒」：给 agent 一个可主动调用的自检入口。
- 无法验证执行的纪律，至少要求留下可审计痕迹（如报告附「已自问」声明）。

## 台账配套

守卫拒收/放行均应可回溯：lc 用 `data/arch_ledger/` 文件台账 + verify_log 证据流。
原则：**台账是守卫的记忆**——没有台账的守卫只有当下，没有历史。
